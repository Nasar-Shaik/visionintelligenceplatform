## ED-0001 — Monorepo: pnpm workspace + Turborepo

- **Date:** 2026-07-27 · **Slice:** 0 (P0-1)
- **Decision:** Single polyglot-friendly monorepo using pnpm workspaces + Turborepo for TS; Python under `ai/` managed separately.
- **Alternatives Considered:** npm/yarn workspaces (weaker perf/dedup); Nx (heavier, opinionated); multi-repo (coordination overhead, contract drift).
- **Reason:** Contract-first design needs one place for `@vip/contracts`; Turborepo gives cached, dependency-ordered task graphs; pnpm gives strict, fast, disk-efficient installs.
- **Impact:** All packages/services/plugins live in one tree; CI installs once; import-graph boundaries are machine-enforceable.
- **Owner:** Claude · **Status:** Accepted · **Future Review:** No

## ED-0021 — Tenant registry is control-plane; tenant-owned data is guard-scoped

- **Date:** 2026-07-28 · **Slice:** P1-1
- **Decision:** Model the `tenants` collection as a **control-plane registry** — each tenant document is keyed by its own id (`tenantId == _id`), `slug` is globally unique, and provisioning/reading a specific tenant is a self-scoped operation. Everything a tenant **owns** (`org_nodes` now; cameras/events later) is **tenant-scoped through the `@vip/tenancy` guard**. Tenant-addressed HTTP routes enforce `context.tenantId === path.tenantId` (cross-tenant → 403).
- **Alternatives Considered:** (a) force the tenant registry itself through the per-tenant guard for _all_ operations — breaks "list all tenants" (an inherently cross-tenant/platform action) and muddles provisioning (no context exists yet); (b) a separate global-scope guard mode now — premature (no platform-admin/global scope until P1-2+).
- **Reason:** Provisioning necessarily precedes any tenant context; the registry is a platform concern. Keeping tenant-_owned_ data strictly behind the guard preserves the fail-closed isolation invariant where it matters, while the registry stays a clean control-plane surface. A global/platform scope is added with authz in P1-2.
- **Impact:** `tenant` service has two collections with different scoping rules (documented in its README + STORAGE); the org-node paths are the P1-1 isolation demonstration. No architecture doc changed.
- **Owner:** Claude · **Status:** Accepted · **Future Review:** Yes (revisit when platform-admin/global scope + "list tenants" land in P1-2)

## ED-0023 — Auth mechanics: scrypt + jose HS256, header-scoped login, refresh reuse-detection, gateway trust boundary

- **Date:** 2026-07-28 · **Slice:** P1-2
- **Decision:** (a) **Password hashing = Node `scrypt`** (built-in, memory-hard), not argon2 (native addon). (b) **Access tokens = jose HS256** with a shared `.env` secret; claims `sub/tid/email/roles` mint the `TenantContext`. (c) **Login is tenant-scoped by the `x-tenant-id` header** (the gateway/subdomain supplies it) so users stay strictly tenant-isolated and email is unique per-tenant. (d) **Refresh tokens are opaque, stored only as a SHA-256 hash** in a control-plane collection, rotated within a _family_; replaying a used token **revokes the whole family** (reuse-detection). (e) The **gateway is the trust boundary**: it validates the token and forwards `x-tenant-id/x-principal-id/x-roles` to upstreams, **stripping any client-supplied** copies.
- **Alternatives Considered:** argon2id (native build — rejected per [ED-0022](ENGINEERING_DECISION_LOG.md) ethos); RS256/JWKS (better for multi-verifier, deferred — HS256 is simpler for one issuer now); global-unique email + cross-tenant login lookup (breaks tenant isolation); JWT/stateless refresh (can't revoke); storing raw refresh tokens (leak risk).
- **Reason:** Minimal dependencies + no native builds; strong, standard security properties (short access TTL, rotation, reuse-detection, per-tenant isolation, spoof-proof context propagation) achievable now.
- **Impact:** New `@vip/auth`, `@vip/permissions`, `@vip/service-gateway`; identity extended with users + auth; `@vip/config` `jwt` group consumed; RS256/JWKS + MFA/SSO documented as future extension points. Full Policy Engine ([28](../architecture/28-POLICY-ENGINE.md)) still plugs in behind `@vip/permissions` in Phase 3.
- **Owner:** Claude · **Status:** Accepted · **Future Review:** Yes (RS256/JWKS split; MFA/SSO; move refresh state to Redis if volume warrants)

## ED-0024 — Camera credential vaulting (`@vip/crypto`), and async zone referential integrity

- **Date:** 2026-07-28 · **Slice:** P1-3
- **Decision:** (a) Camera RTSP/RTMP credentials are **vaulted at rest** with a new shared package **`@vip/crypto`** — authenticated **AES-256-GCM** envelopes (`v1.gcm.<iv>.<tag>.<ct>`) over a 32-byte key derived (scrypt) from an `.env` app secret (`CREDENTIAL_ENCRYPTION_KEY`, ADR-0018 — **no external KMS**). The stored record holds only the cipher; responses/events/logs expose `hasCredentials: boolean` and never the plaintext or cipher. A `streamUrl` may **not** embed `user:pass@` (contract-enforced) so credentials are only ever in the vault. (b) The **Camera context owns cameras**; the **location hierarchy (org→…→zone) stays owned by the Tenant context** (P1-1 `OrgNode`) per frozen [22-BOUNDED-CONTEXTS §1/§3] — a camera references its `zoneId`, it does not redefine the tree (the blueprint's "own the hierarchy" wording is reconciled to the bounded-context authority). (c) **Zone referential integrity is validated asynchronously, not by a synchronous cross-service call:** P1-3 stores/validates the `zoneId`'s shape + tenant-scoping but does not call the tenant service to confirm existence; the camera context will reconcile against `tenant.hierarchy.changed` over the event backbone (P1-5). (d) The camera service **verifies the identity-issued Bearer token itself** (defence-in-depth: `iss=identity`, `aud=vip`, same as the gateway) rather than trusting forwarded headers; routes are permission-gated (`camera:create|read|update|delete`).
- **Alternatives Considered:** external secrets manager / KMS envelope (**rejected — `.env`-only mandate, ADR-0018**); argon2/libsodium for encryption (native builds — rejected per [ED-0022](ENGINEERING_DECISION_LOG.md) ethos, `node:crypto` suffices); putting credential encryption inside `@vip/auth` (conflates principal-auth with symmetric vaulting — a focused `@vip/crypto` is reused later by connectors + edge storage); a synchronous camera→tenant HTTP call to verify the zone on every create (couples the contexts at runtime, breaks independent deployability — 22 golden rule); trusting gateway-forwarded `x-*` headers instead of re-verifying the token (weaker per-service posture).
- **Reason:** Meets the encrypt-at-rest requirement with zero new external dependencies and no native builds, keeps bounded contexts independently deployable (cross-context reads via events, not sync calls), and reuses the exact P1-2 authz plumbing.
- **Impact:** New `@vip/crypto` package + `@vip/config` `crypto` group + `@vip/service-camera`; `@vip/contracts` gains camera schemas + `camera.registered|updated|removed|health.changed` events (15 JSON schemas total); gateway gains the `camera` upstream (`CAMERA_URL`). Async zone integrity is tracked as **[TD-3](../../tracking/TECH-DEBT.md)**. No frozen architecture doc (01–28) edited. Envelope `v1` tag reserves room for key rotation / DEK-per-record later.
- **Owner:** Claude · **Status:** Accepted · **Future Review:** Yes (enforce zone existence once the event backbone lands P1-5; key rotation tooling; RS256/JWKS shared with P1-2)

## ED-0025 — Media ingestion: ffmpeg-binary decoder, tenant-prefixed object storage, service-to-service credential resolve

- **Date:** 2026-07-28 · **Slice:** P1-4
- **Decision:** (a) **Storage isolation is a shared wrapper, not per-service discipline** — new **`@vip/storage`** provides `TenantObjectStore`, the MinIO counterpart of the `@vip/tenancy` Mongo guard: it enforces the `{tenantId}/…` object prefix (fail-closed on blank tenant / key escape) over an AWS-SDK-v3 `S3ObjectStore` (pure-JS, MinIO path-style). Recordings land under `{tenantId}/{cameraId}/recordings/…`; access is signed-URL only. (b) **The decoder is the ffmpeg BINARY, spawned as a child process** — a system dependency, NOT a native npm addon, so it respects the no-native-build policy ([ED-0022](ENGINEERING_DECISION_LOG.md) ethos). One invocation records rolling MP4 segments AND pipes JPEG frames for perception. (c) **Media resolves camera credentials via a Camera-context INTERNAL endpoint** (`GET /internal/cameras/:id/stream`) — the single sanctioned decryption point — authenticated by a shared **`INTERNAL_API_KEY`** (`x-internal-key`, constant-time compared, `.env` only, ADR-0018); the gateway **strips** any client-supplied `x-internal-key` so it can only be satisfied by a trusted service (defence-in-depth). Credentials are used transiently, never stored/logged. (d) **Stream state is in-memory** (per-camera workers), reconnect uses **exponential backoff**, and storage-write failures **degrade** (logged) without blocking the live path. ## ED-0042 — AI-5c Inference Scheduling & Resource Management: decide whose frame runs next, refuse what cannot be served, degrade instead of failing

- **Date:** 2026-08-01 · **Phase:** Production Readiness (AI-5, slice AI-5c) · **Architect review:** AI-5b ACCEPTED with 10 forward recommendations; AI-5c plan approved + 8 + 7 further refinements; AI-5c code review pending
- **Decision:** Implement **stage 4 of the reference architecture** (the Inference Scheduler, specified since [AI_EXECUTION_ARCHITECTURE](../architecture/future/AI_EXECUTION_ARCHITECTURE.md) was written — _not_ a new layer), **in `ai/inference` (no new service)**, with **no change to the five frozen v1.0 contracts** (ED-0039 upheld). AI-5b gave each session its own bounded queue, protecting a session from its own camera; AI-5c protects sessions **from each other**. Three cooperating pieces behind the unchanged `/infer` + `ModelAdapter` seam: an **`AdmissionController`** that estimates a session's cost and refuses work that cannot be served safely (typed reasons `session-capacity`/`compute-capacity`/`reserve-protected`/`no-compatible-resource` — different causes need different operator responses); an **`InferenceScheduler`** using **weighted-fair rotation** by default so priority influences share **without permitting starvation** (`maxConsecutivePerSession` bounds any run, even under `strict-priority`); and a **`ResourceGovernor`** walking an **ordered, reversible, hysteretic degradation ladder** (`none -> reduced-fps -> reduced-resolution -> reduced-behaviors -> shedding-frames -> suspended`) so the runtime spends the cheapest analytical quality first and **never hard-fails a session**. Compute is **hardware-independent**: `ComputeResource` describes capacity in **abstract dimensionless units** (never cores or VRAM — the only thing every accelerator shares is "how much concurrent work fits"), covering cpu/cuda/tensorrt/openvino/metal/tpu/npu as registry entries rather than scheduler branches, with **node-qualified ids** (`node-a/cuda:0`) so future distributed scheduling adds resources instead of requiring a redesign. A **capacity reservation** (default 10%, `reserveFor: [critical]`) is held back from ordinary admission because a runtime at 100% committed **cannot recover from its own success** — nothing restarts and no critical camera starts. Degradation is **predictive**: a least-squares `Trend` projects queue utilization forward, so the governor acts while headroom remains rather than after frames are lost. **Per-session accounting** (`SessionResourceUsage`) attributes CPU/memory/GPU from measured work — documented explicitly as **estimates**, since one process has no per-session kernel accounting and false precision would mislead capacity decisions — alongside **`SessionSla`** (target vs actual FPS/latency, `met`, attainment %) so scheduling is data-driven. An **`AnalyzerCostModel`** makes the `reduced-behaviors` rung disable the **most expensive** analyzers first and **never** a `protectedAnalyzers` entry (fire/intrusion stay on). **Seven portable `DeploymentProfile`s** (retail/warehouse/office/school/hospital/factory/parking) express operational defaults — FPS, sampling, enabled behaviors, queue limits, priorities, degradation ceiling — as **configuration, not code**, and are deliberately distinct from the AI-4 `BehaviorProfile` (_what to detect_ vs _how hard to work_), so a hospital can run retail's behavior set on hospital-grade operational settings. Every scheduler action records a **structured decision** (identity, typed action, typed reason, triggering measurement). `CameraCapabilities` is **extended additively** (`fpsRange`/`streamProfiles`/`onvif`) and the runtime **reads** it instead of **probing** devices. `RuntimeMetrics` is partitioned into **operational vs AI** groups (`METRIC_GROUPS`) — one producer, two audiences. Benchmarking gains **baseline comparison** (`compare_reports`, `--baseline`) that refuses to compare runs with differing configuration/hardware fingerprints and **exits non-zero on regression**, making "never merge optimizations without measurable improvement" enforced rather than requested. Contracts **+9 -> 88 schemas**, all operational.
- **Alternatives Considered:** (a) a new scheduling service — rejected (stage 4 was always in-runtime; no infrastructure expansion); (b) strict priority as the default — rejected (the common production failure is one busy camera starving seven quiet ones, not an important camera losing to an unimportant one; weighted-fair gives priority influence without starvation); (c) hard-failing an overloaded session — rejected (a camera at 2 fps still detects intruders; a failed session detects nothing); (d) capacity expressed in cores/VRAM — rejected (couples the scheduler to every vendor's arithmetic; abstract units are the seam); (e) reacting only to observed overload — rejected (by the time the queue is full, frames are already lost); (f) per-thread kernel resource measurement — rejected for now (one process; attribution from measured work is honest and documented as estimated); (g) treating every analyzer as equally expensive during degradation — rejected (refinement 4: cost-ordered, with protected safety analyzers); (h) folding operational settings into the AI-4 `BehaviorProfile` — rejected (perception intent and operational envelope must vary independently); (i) letting the governor suspend every session — **rejected after the 32-camera simulation proved it collapses fleet throughput to a third**; the governor now never suspends the last runnable session.
- **Reason:** A fixed-size box running many cameras must answer three questions AI-5b left open: who runs next, who is allowed to start, and what gives way under pressure. Answering them with fairness, typed refusals, and ordered degradation is the difference between a runtime that survives its worst hour and one that fails all of its cameras at once. Doing it behind abstract compute units keeps the same code correct on a laptop, an RTX box, and (later) a cluster.
- **Impact:** `@vip/contracts/inference` (+9 -> **88 schemas**: ComputeResource/SchedulerPolicy/SchedulerStats/SchedulerDecision/SessionResourceUsage/SessionSla/AdmissionVerdict/ResourceSnapshot/DeploymentProfile, plus `AnalyzerCostModel`/`METRIC_GROUPS`/`DEGRADATION_LADDER`/`PRIORITY_WEIGHTS`); additive `CameraCapabilities` + `BenchmarkComparison`; new runtime modules (`compute.py`, `resources.py`, `scheduler.py`, `scheduler_sim.py`, `deployment.py`) + 7 deployment profiles; additive HTTP (`GET /scheduler`, `/sla`, `/resources`); `INFERENCE_DEPLOYMENT_PROFILE`; benchmark `--baseline` regression gate. **Contracts 181 / Python 355** (+108). No frozen-doc (01-28) change, no new service, no perception-contract change (freeze intact), boundary held (events only). New governance doc [PRODUCTION_COMPATIBILITY](../architecture/future/PRODUCTION_COMPATIBILITY.md) (offline-replay guarantee, DVR/NVR/ONVIF compatibility matrix, real-hardware certification checklist for AI-5e, frozen-architecture guardrail). Opens **AI-5d** (health/auto-recovery + model lifecycle).

## ED-0043 — AI-5d Health Monitoring, Auto-Recovery & Model Lifecycle: make a session survive itself over time

- **Date:** 2026-08-01 · **Phase:** Production Readiness (AI-5, slice AI-5d) · **Architect review:** AI-5c ACCEPTED with 9 forward recommendations; AI-5d plan approved + 8 further recommendations; AI-5d code review pending
- **Decision:** Add the **time dimension** to the runtime — **in `ai/inference` (no new service)**, with **no change to the five frozen v1.0 contracts** (ED-0039 upheld) and **no new architectural layer** (AI-5d supervises stages that already exist; model lifecycle sits behind the unchanged `ModelAdapter` seam). AI-5b made a session survive its camera and AI-5c made it survive its neighbours; neither made it survive **itself over time**. Four pieces with strictly separate responsibilities: **`HealthMonitor`** produces evidence (a 0–100 score decomposed across **connection · inference · scheduler · resources · recovery**, every component **required** in the output because a report that omits a subsystem is the one that misdirects an operator, plus a `Trend` per indicator so it reports where health is _heading_); **`ResourceGovernor`** remains the **only** component that moves a session down the ladder — a projected health decline becomes one more pressure reason (`predicted-health-decline`) on its existing path, because two components able to degrade a session independently is how you get an oscillation nobody can debug; **`AutoRecovery`** decides recovery within a **budget expressed as external configuration** (retail 3 restarts · factory 10 · bank unlimited with long cooldown · healthcare operator-approval-only — all four shipped as deployment profiles) and the runner merely supplies the executor, preserving the AI-5c "report up, apply down" seam; **`ModelLifecycleManager`** stages every version change as `warming → validating → switching → draining → active`, with rollback on the same mechanism run backwards. Recovery **executes the frozen AI-5b taxonomy** rather than adding judgement, and `configuration` failures are **never retried** — enforced as a code-level invariant that _rejects_ a profile asking for it, since a wrong RTSP URL does not become right on the four-thousandth attempt and retrying it buries the one log line that would have told an operator what to fix. Zero downtime rests on one indirection: `VideoAnalyzer` holds a **`ModelSlot`** and reads `slot.adapter` **per frame**, so promotion is an attribute assignment — no session stops, no queue drains — and `draining` keeps the outgoing model warm so a frame that entered under vN finishes under vN. Model validation is **operational, explicitly not accuracy**: `artifact-loads`/`inference-runs`/`output-structure`/`latency-budget`/`detection-comparability` catch a corrupt artifact, a wrong input shape, a 10× latency regression and a model that silently detects nothing; certifying recall needs labelled footage and is AI-5e. **Progressive restoration** replaces ladder reversal: each degradation pushes a **`RestoreStep`** recording exactly what it removed (which analyzers, which FPS, which scale) and each recovery pops it, making exact-reverse restoration **structural rather than intended** — a rung says _where_ a session is, only the stack says _what was taken_. **Anti-oscillation** is applied at two levels and is deliberately **direction-aware**: `AutoRecovery` defers a restart inside its stabilization window, and the governor requires N observations before a **direction reversal** only — two escalations in a row are not oscillation but the ladder doing its job, and delaying them would strand a drowning session at a rung that cannot save it; suppression is edge-triggered so the guard does not flood the log it protects. A **`DiagnosticsJournal`** merges admission · scheduling · degradation · recovery · restart · model transitions · failures into one bounded, tenant-scoped stream **as a sink on the `OperationalLog` a session already writes to** (a second emitter would recreate the problem it solves), rendered both newest-first for machines and **oldest-first as a timeline** for humans. Contracts **+14 → 102 schemas**, all operational.
- **Alternatives Considered:** (a) letting `HealthMonitor` degrade sessions directly — rejected (two degradation authorities produce undebuggable oscillation; health emits evidence only); (b) a binary healthy/unhealthy flag — rejected (rec 2: `overallHealth = 83` is not actionable; component scores name the subsystem); (c) counting sampled-away frames in the health score — rejected again here (a correctly-tuned 0.5-fps camera would report as sick and operators would raise FPS to make the number look good); (d) scoring an absent reading as zero — rejected (a box with no GPU probe is not unhealthy for lacking a GPU; unobservable components score 100); (e) reversing the degradation ladder by rung — rejected (rec 4: re-enabling a _different_ analyzer is the same rung count and the wrong outcome; the restoration stack makes it exact); (f) a single stabilization window blocking every transition — **rejected after it broke two existing scheduler tests by delaying escalation under sustained pressure**; the guard now applies to direction reversals only; (g) restarting a session on a health decline — rejected (health degrades via the governor; only a _failure_ justifies a restart); (h) allowing policy to auto-recover `configuration` failures — rejected and made impossible (a misconfigured profile must not be able to create a restart loop against an operator error); (i) gating a model switch on a latency-regression bound at any magnitude — **rejected after stub timings made the gate fail on timer noise**; the bound is skipped when both models measure under 1 ms/frame; (j) a background recovery thread — rejected (an architectural addition; recovery runs on the supervisor's existing sweep); (k) inventing "recovery time" / "health stability" benchmark KPIs — rejected (the harness runs workloads, not fault injection; the scenario suite gates operational logic instead); (l) retaining a stopped session's journal — rejected (unreachable history is a leak, not a diagnostic).
- **Reason:** Operating a fleet is a question about _time_, not a snapshot: a camera reconnecting every ninety seconds, dropping a third of its frames and missing its SLA reported `healthy` right up until it stopped. AI-5d replaces that single bit with a decomposed, projected score; turns a permanent failure into a budgeted recovery an operator can reason about; and makes a model upgrade something other than an instant flip under eight running cameras. Doing all three as **policy read from deployment profiles** is what lets one runtime behave correctly in a hospital and in a parking lot.
- **Impact:** `@vip/contracts/inference` (+14 → **102 schemas**: HealthScore/HealthIndicator/HealthPolicy/RecoveryReason/RecoveryAttempt/RecoveryPolicy/RestoreStep/ModelTransition/ModelValidationResult/ModelLifecycleHistory/ModelLifecyclePolicy/DiagnosticEntry/TimelineEntry/SessionOperationalDiagnostics, plus `HealthComponent`/`RecoverySubsystem`/`ModelTransitionState`/`DiagnosticKind` and two `SchedulerReason` members); additive `SessionResourceUsage` (`disabledAnalyzers`/`healthScore`) and `DeploymentProfile` (`health`/`recovery`/`modelLifecycle`); new runtime modules (`health.py`, `recovery.py`, `model_lifecycle.py`, `journal.py`, `production_sim.py`); `video_analyzer` reads its adapter through a `ModelSlot` (behavior-identical when no slot is supplied); all 7 deployment profiles gain recovery/health policy; additive HTTP (`GET /sessions/{id}/health|diagnostics|timeline|recovery`, `GET /sessions-health`, `GET /fleet-health`, `POST /sessions/{id}/recover`); benchmark `--scenarios` operational gate. **Contracts 208 / Python 506** (+151). AI-5a baseline re-run: PASS, 0.00% dropped. No frozen-doc (01–28) change, no new service, no perception-contract change (freeze intact), boundary held (events only). ### ED-0043 addendum — AI-5d follow-up refinements (accepted review, 8 recommendations)

- **Date:** 2026-08-01 · **Architect review:** AI-5d ACCEPTED; 8 further recommendations, all folded in without a new layer.
- **Decision:** (1) **`RecoveryHistory`** — a permanent, tenant-scoped record (failure category · action · duration · outcome · restart count · stabilization period · final state) held **separately from the `RecoveryLedger`** and deliberately **not cleared on session teardown**: the ledger is budget accounting, the history is the operational record, and forgetting it when a session stops erases the pattern exactly when it becomes interesting. The final state is resolved by a **callable evaluated after the executor runs**, because reading it beforehand records the state the recovery was meant to fix. (2) **Health trend visualization** — every component carries a rolling window (`componentTrends`), with `sparkline()` and `render_components()` producing the operator view the Architect sketched; the bar renders the _current_ score and the arrow the _direction_, since one glyph carrying both would be readable as neither. (3) **Model deployment history persistence** — `export_history()`/`import_history()` make the record durable as JSON **without a database or a service**, and import is **idempotent** and **terminal-only** (an in-flight rollout is not resumable: its warmed adapter no longer exists), re-sorting by start time so restored records interleave with live ones instead of appearing to follow them. (4) **Recovery profiles as files** — `profiles/recovery/*.json` (retail/factory/bank/healthcare/conservative) ship as ordinary examples of a mechanism, not privileged built-ins, so a customer authors a new archetype by adding a file. (5) **`FailureAnalytics`** — most common category, average recovery time, success %, restart total, average stabilization, cameras affected; averaged over **executed** recoveries only (including refusals would drag the mean toward zero and make a deployment that never recovers look fastest) and **read by no runtime path**, because feeding last week's averages into a live control loop makes a system react to history instead of conditions. (6) The direction-aware oscillation rule is now documented in the tracker, the governor docstring and this log. (7) **Seven new simulations → 17 total**: partial GPU failure (capacity shrinking beneath live allocations), mixed hardware cluster (five resources across three nodes), network partition (whole-fleet loss and recovery), **RTSP credential failure** (0 restarts, 0 budget spent, every attempt escalated — the suite's most important negative case), gradual resource exhaustion (degrades on the trend, before saturation), overnight continuous (10,000 ticks with no drift in throughput or fairness), rolling model deployment (a failed rollout never leaves a split fleet). (8) Contracts **+2 → 104** (`RecoveryRecord`, `FailureAnalytics`) plus one additive `HealthScore.componentTrends` — the minimum needed to surface the above over HTTP.
- **Two findings from the new simulations:** the partition scenario initially asserted against _requested_ rather than _admitted_ cameras, so it was testing the admission reserve rather than the partition; and `ModelLifecycleHistory.versionPath` silently dropped a rollback whose incumbent version was unknown, making the path read as though nothing had been attempted — a rollback now always records a return.

No new service, no new layer, frozen five untouched. **AI-5e authorized** — the final production-readiness milestone for AI Runtime Architecture v1.0, and the last AI runtime milestone: the Architect has directed that no AI-6 follow.

- **Date:** 2026-08-01 · **Phase:** Production Readiness (AI-5, slice AI-5e — **final milestone of AI Runtime Architecture v1.0**) · **Architect review:** AI-5d ACCEPTED; AI-5e authorized and explicitly **redefined** as the _Production Certification Framework_ milestone ("The software can build the framework. - **Decision:** Build everything required for production certification — **in `ai/inference` (no new service, no new runtime layer)**, with **no change to the five frozen v1.0 contracts** (ED-0039 upheld) — and make it **structurally incapable of certifying itself**. The organising idea is **`EvidenceClass`** (`simulated` → `recorded-footage` → `hardware`), threaded through every check, report and promotion, with three rules expressed in code rather than in prose: a report is only as strong as its **weakest** check (`weakest()` takes the minimum); `certified` is **unreachable** without `hardware` (`CertificationHarness._status_for()`); and `production` maturity is **unreachable** without `hardware` (`maturity.promote()`). Delivered: (1) **ONVIF discovery + capability negotiation** (`onvif.py`) behind two Protocol seams — `DiscoveryTransport` and `SoapTransport`, each with a real and a deterministic simulated implementation — so the whole path is unit-tested with no network, camera or thread; the runtime **consumes** declared `CameraCapabilities` rather than probing (probing costs a connection and a decode per session start; on a 64-camera site after a power cut that is 64 connections nobody needed); the WS-Security password **never enters the envelope** (SHA-1 digest only, because ONVIF is routinely spoken over plain HTTP inside a LAN); credentials in a device-returned stream URI are **stripped to a path** (devices hand back `rtsp://admin:…@…`, and storing that puts a password in the camera record). (2) **`RtspStreamSource`** — a named subclass of `OpenCvStreamSource`, not a new implementation: profile selection **delegated to the existing `resolve_stream_settings()`** so there is exactly one implementation of "which stream do we analyze", TCP transport by default, and the **declared** source type preserved rather than rewritten. (3) **Certification harness** driving the **real** `SessionSupervisor` → `SessionRunner` → `StreamPipeline` and reading only diagnostics the runtime already publishes; two-phase, so checks only a human can make (`reconnect-recovery`, `clean-shutdown`) stay `not-executed` **and keep blocking** — an incomplete run reads as incomplete, never as a pass with gaps. (4) **Compatibility matrix** — 11 devices as data files, **all `Pending Validation`**, with `certify()` the only mutator and a dataclass invariant that **refuses to construct a `certified` entry** with no evidence or with sub-hardware evidence. (5) **Soak framework** measuring **drift, not level** (every failure that matters in surveillance is slow), judging only the **adverse direction** (memory falling 30% is not a failure; fps falling 30% is), reporting a shortfall as a blocker, and driven by an **injected clock** so a 72-hour soak is asserted in microseconds. (6) **Edge packaging** — 5 targets declared as data; unprivileged, `tini`-init (OpenCV leaves decoder subprocesses behind, and without an init a long-running container accumulates zombies until it cannot fork), RTSP-over-TCP, health-checking the runtime's own `/health`. (7) **Promotion as a function** taking report **ids** rather than claims, with `certification_status`/`soak_passed`/`benchmark_accepted` because an id proves a run _happened_, not that it _succeeded_; every blocker reported at once; demotion needs no evidence. (8) **Customer validation bundle** with `redact_config()` applied **unconditionally** — the bundle travels by email between organisations. Plus, per the re-prioritization: the **CCTV dataset library** (18 scenarios; footage DVC-only and `.gitignore`-refused from git; a licence or consent basis **required** to load), the **accuracy evaluator** (both directions scored, behaviours counted **once per behaviorId**, `incident` expectations **deferred** rather than scored, `footage-missing` **never** a pass), and the **AI Playground workbench** (`timeline.json` answering "what happened, in order?", `incidents.json` labelled as candidates, `evidence.json` always `not-registered`, `performance.json` as a cost breakdown, and a self-contained `report.html` with no CDN, no script and escaped text).
- **Alternatives Considered:** (a) letting a complete simulated run report `certified` — **rejected as the single thing that would invalidate the milestone**; a framework that certifies itself from its own simulations converts a known unknown into a false assurance someone will quote to a customer, and the negative control (`test_a_flawless_simulated_run_is_still_not_certified`) exists so that rule cannot be quietly removed; (b) treating a `skipped` or `not-executed` check as non-blocking — rejected ("we never measured it" is not evidence that it works); (c) a second "which stream do we analyze" implementation inside `RtspStreamSource` — rejected (it would eventually disagree with the scheduler's, surfacing as a camera that benchmarks against the sub-stream and runs against the main one); (d) rewriting a declared `onvif` source type to `rtsp` — rejected and caught by an existing test (the runtime dispatches on declared type and must never launder it); (e) judging soak drift by magnitude — rejected (would fail every run where the machine got quieter overnight); (f) failing a soak whose first sample was zero — rejected (a reading taken before warm-up would fail every run); (g) an open-string scenario category — rejected (cases would accumulate under three spellings of "loitering" and the corpus would stop being a regression suite); (h) scoring `incident` expectations against the AI runtime — rejected (incidents belong to the rules service; scoring against an output it does not own is meaningless in both directions); (i) letting a footage-less run report `accepted` — rejected (`summarize()` requires at least one case actually evaluated); (j) letting ONVIF discovery change a registry status — rejected (a successful `GetDeviceInformation` mistaken for a passing certification is the easiest way for the registry to start lying); (k) pixel-exact accuracy expectations — rejected (the corpus is not labelled for IoU and holding it to one would be expensive and dishonest about what it proves); (l) a `report.html` using a CDN — rejected (customer demonstrations happen on laptops with no network).
- **Two implementation bugs the realistic fixtures found:** WS-Discovery parsing read the service address from `a:Address` inside the `EndpointReference` — that field is the device's `urn:uuid:` identity, not a callable URL (the address is in `d:XAddrs`), so discovery returned **zero devices** against any real response; and the certification `connect` check initially conflated "never opened" with "opened and delivered nothing", collapsing the two most diagnostically distinct camera failures into one verdict.
- **Reason:** Everything through AI-5d was proved in simulation. Simulation proves the **architecture**; it cannot prove a Hikvision on a warehouse VLAN streams for 72 hours without the decoder wedging, and it cannot prove the system notices a shoplifter. AI-5e builds what answers those questions and deliberately stops short of answering them, because the answers require hardware and footage that do not yet exist. Making the refusal **structural** — not a convention, not a paragraph — is what makes the framework worth having: the first time it is used in anger will be by someone under commercial pressure to report a green result.

## ED-0046 — P-1 Camera & Device Management: ONVIF onboarding, DVR/NVR bulk add, and the first product slice

- **Date:** 2026-08-01 · **Phase:** **Product phase (P-1)** — the first milestone after AI Runtime v1.0 closure · **Architect direction:** "Proceed with the Vision Intelligence Platform product phase, using the completed AI Runtime as the production inference engine." First slice and discovery placement both chosen by the Architect.
- **Decision:** Implement camera & device management end to end — contracts, service, runtime capability, console — filling the `Cameras` placeholder and the `POST /cameras/discover` **501 that has been waiting since P1-4** with exactly what AI-5e built. Placement per [ADR-0023](../adr/ADR-0023-onvif-discovery-placement.md): **the camera service owns the onboarding workflow and calls ONVIF discovery as a read-only runtime capability**, behind a `DiscoveryProvider` port, rather than growing a second ONVIF stack in TypeScript that would drift from the tested one. Four decisions carry the slice: (1) **`DiscoveredCamera` is a distinct shape from `Camera`** — a discovered device has no tenant, no id, no zone and no credentials, and giving it the same type is how a UI ends up implying the platform is already watching something it has never connected to; (2) **"could not run" is a first-class status, never an empty list** (`DiscoverCamerasResult.unavailable`) — an installer told "no cameras found" goes and checks the cameras, when the real problem is a blocked multicast, and that mistake costs an afternoon at the wrong end of a building; (3) **already-onboarded devices are shown greyed, not hidden** — someone re-scanning a half-configured site must be able to tell "already added" from "did not answer", which hiding makes indistinguishable, with matching done on a **normalized** stream URL (scheme/host case-insensitive per RFC 3986, path preserved because DVR channel paths are case-sensitive, trailing slash dropped); (4) **bulk onboarding treats partial success as the expected outcome** — one bad channel in a 16-channel DVR must not discard the other fifteen, so each camera is created independently with a per-item result, and the whole thing is deliberately **not** transactional. Credentials never travel: the ONVIF password is read from the runtime's own environment rather than passed through the gateway and a JSON body, a device-returned credentialed stream URI is **rebuilt from host + path** instead of being stored, and the console refuses a credentialed URL with an explanation rather than letting the contract 400 it.
- **A design flaw the tests exposed, fixed rather than papered over:** `BulkCreateCamerasInput.cameras` was first typed `CreateCameraInput[]`, which made one malformed channel reject all sixteen **at parse time** — and made `BulkCreateCameraResult.error` a promise the shape could never keep, since a schema failure would never reach it. The envelope is now `unknown[]` validated **per item** against the same contract. The cost (callers lose compile-time element typing) is recorded in the contract's own doc comment.
- **Alternatives Considered:** (a) reimplementing WS-Discovery + SOAP in TypeScript — rejected, two ONVIF stacks drift and the drift surfaces as a camera that onboards with one set of capabilities and streams with another (ADR-0023); (b) extracting ONVIF into a shared component now — the purest separation, deferred on timing (it would rewrite AI-5e code the day the runtime was closed) and recorded in ADR-0023 as the revisit trigger; (c) modelling discovery as a TanStack **query** — rejected, a probe is an active multicast operation and a query would let a window-focus refetch silently re-scan a customer's estate; (d) hiding already-onboarded devices — rejected (see above); (e) wrapping bulk onboarding in a transaction — rejected, an installer who mistyped channel 7 would lose the six that were right; (f) letting discovery write to the camera inventory — rejected, discovery returns candidates and onboarding stays a deliberate act; (g) letting ONVIF discovery update a device's certification status — rejected and separately test-guarded, since a successful `GetDeviceInformation` mistaken for a passing certification run is the easiest way for the compatibility registry to start lying.
- **Reason:** Every other product capability needs cameras configured first, and the platform's onboarding story was a 501 and a placeholder page. This slice turns the AI-5e ONVIF work into the thing a customer actually experiences on day one of an install — and does it without weakening the runtime's perception-only boundary, by making the exception explicit, bounded and documented instead of implicit.
- **Impact:** `@vip/contracts/camera` +4 schemas (**127 total**): `DiscoveredCamera`, `DiscoverCamerasResult`, `BulkCreateCamerasInput`, `BulkCreateCamerasResult`, plus `DiscoverCamerasInput.timeoutSeconds`; AI runtime gains `POST /discovery/onvif` (read-only, creates no session, touches no tenant data); `services/camera` gains the `DiscoveryProvider` port + `HttpDiscoveryProvider`/`UnavailableDiscoveryProvider`, `CameraService.discover()`/`createMany()`, `POST /cameras/discover` (now implemented) and `POST /cameras/bulk`, and optional `CAMERA_DISCOVERY_URL`; `apps/console` gains the real `CamerasPage` (list · search · health filter · detail sheet · delete), `DiscoveryDialog`, `AddCameraDialog` (single + DVR/NVR channel templates for Hikvision/Dahua-CP Plus/UNV/custom), and full camera CRUD in the API layer. **Contracts 243 · Python 783 · camera service 51 · console 58.** Typecheck 28 · lint 20 · build 19 · import-graph 0 violations · format clean. No new service, no new runtime layer, the five perception contracts untouched.

## ED-0047 — P-2 Camera Lifecycle, Identity & Operational Health: a device state means a measurement

- **Date:** 2026-08-02 · **Phase:** Product phase (P-2) · **Architect direction:** P-1 review ("Introduce an explicit lifecycle for managed cameras"; "Separate camera health from AI session health"; "Discovery should populate a capability cache"; "Every camera should have a stable internal identity independent of IP") and the P-2 mid-flight review ("Prevent invalid transitions such as Retired → Connected without reinstatement"; "POST /streams/validate should return a complete validation report rather than only success/failure"; "Evidence should remain the single source of truth across the platform").
- **Decision:** Give managed cameras an explicit lifecycle, and make the states that describe a physical device **enterable only from a measurement of that physical device**. `connected` · `monitoring` · `degraded` · `offline` require `evidence: 'measured'` **and** `EvidenceClass: hardware`; `discovered` · `validated` · `configured` are declared; `retired` is administrative and is **not** reversible by a health check — reinstatement returns a camera to `configured`, never to whatever measured state it held before. The measurement is `POST /streams/validate` on the AI runtime, which opens the source, reads frames, and returns an **ordered check report** (`reachability → authentication → stream-open → frames-received → codec → resolution → fps → latency → jitter`) in which a failure leaves every later check `not-executed` rather than `fail`. Five supporting decisions: (1) **`EvidenceClass` is lifted to `contracts/common/evidence.ts`** — certification, capability maturity, benchmarks and the device lifecycle now read one enum, so one measurement means one thing platform-wide; (2) **device identity is separated from network identity** — the ONVIF endpoint UUID that the WS-Discovery parser was already reading _and discarding_ is now captured, stored at onboarding and matched **first**, so a camera whose DHCP lease moved it is recognised (`addressChanged`) instead of being offered as a new device; (3) **capabilities are cached with their provenance** (`cacheVersion` · `firmware` · `discoveredAt` · `lastRefreshedAt` · `refreshReason` · `refreshCount`), because without recording what they were read _against_, "has anything changed?" is unanswerable and the only safe behaviour left is to re-query every device on every session start; (4) **one bounded timeline, not two** — state changes, firmware moves, capability reads, credential rotations and probes interleave in a single 50-entry `CameraTimeline`, because the things that _explain_ a state change are usually not themselves state changes; (5) **`retire` is not `delete`** — decommissioning keeps the record and its history, which an incident investigation may need months later.
- **Alternatives Considered:** (a) deriving `connected` from the existing `health.status` — rejected, that field was only ever set by _configuration_ validation, so it would manufacture measured evidence from a declaration and silently backfill the whole inventory as connected; (b) letting any successful probe advance the lifecycle regardless of source — rejected, demo and CI run simulated sources by construction, so the first consequence is a fictional connected estate and the second is nobody believing the field again; (c) a TypeScript RTSP client in the camera service — rejected on ADR-0023 grounds, a second decode path drifts from the one analysis actually uses, so a camera could pass its test and fail in production; (d) a free-form status string instead of a transition map — rejected, `retired` degrades into a label the next scheduled health check overwrites; (e) keeping one `health` field for camera and session health — rejected per direction, a camera can be healthy while its session has crashed and a session can run happily against a frozen frame; (f) two histories (lifecycle transitions + an operational timeline) — rejected as duplication, one list with typed event kinds answers both questions; (g) re-broadcasting WS-Discovery to refresh one camera's capabilities — rejected, multicast never leaves the local segment so a camera on another VLAN would look like it had vanished; a directed negotiation of the known endpoint was added instead.
- **A gap the tests exposed, fixed rather than papered over:** identity matching was fully unit-tested and **inert end to end** — nothing persisted a device's identity, because `CreateCameraInput` had no `identity` field, so the DHCP case could never fire in production. Adding it closed the loop, and the HTTP test now proves the round trip rather than the domain function.
- **Reason:** P-1 produced an inventory, which records what somebody configured and says nothing about whether it works — every camera ever onboarded showed `health: unknown` because nothing had opened a stream. P-2 answers "does it work?" and, more importantly, fixes what the platform is _entitled to claim_ when it answers. The alternative is a system that talks itself into "connected" from its own simulations, which is precisely the failure AI-5e made impossible for hardware certification and would otherwise have re-entered through the device lifecycle.
- **Impact:** `@vip/contracts` **+10 → 137 schemas**: `CameraLifecycle`, `CameraTimelineEntry`, `CameraDeviceIdentity`, `CameraOperationalHealth`, `CameraHealthSummary`, `CapabilityCache`, `CapabilityRefreshResult`, `StreamProbeRequest`, `StreamProbeResult`, `CameraProbeReport`; `EvidenceClass` moved to `common/evidence.ts` (imported, not re-exported, so the barrel exports exactly one). AI runtime gains `ai/inference/stream_probe.py` + `POST /streams/validate`, a directed-endpoint branch on `POST /discovery/onvif`, and `DiscoveredDevice.endpoint_uuid`/`to_identity()`. `services/camera` gains `domain/lifecycle.ts` (transition map + evidence gate), `domain/identity.ts`, `domain/capability-cache.ts`, `domain/health-history.ts`, the `StreamProbe` port, and `POST /cameras/:id/probe` · `/capabilities/refresh` · `/retire` · `/reinstate` · `GET /cameras/:id/health/summary`. Console gains the lifecycle column + filter, a measured-health panel that distinguishes _never measured_ from _measured and offline_, the `ProbeResultPanel` installer readout, a timeline, and retire/reinstate. **Contracts 264 · Python 816 · camera 112 · console 67.** Typecheck · lint · build · import-graph 0 violations · format clean. No new service, no new runtime layer, the five frozen perception contracts untouched. ## ED-0048 — P-2.1 Diagnostic Depth: what changed, when, and which step failed

- **Date:** 2026-08-02 · **Phase:** Product phase (P-2.1) · **Architect direction:** P-2 acceptance ("Do not overwrite device identity"; "Capability refresh should produce a diff"; "Expand the validation report into a structured diagnostic report"; "Every probe report should include Probe Version, Runtime Version, Configuration Version, Evidence Class") and the P-2.1 acceptance ("Measure the duration of every probe stage individually"; "Classify capability changes"; "Identity matching should report confidence"; "Never silently use stale capabilities"; "Timeline entries should include reason codes"; "Continue enforcing typed failures… These should remain mutually exclusive"; "Keep the probe pipeline protocol-neutral"; "Console — Visualization only").
- **Decision:** Turn the P-2 probe into a **staged, timed, typed diagnostic pipeline** and give every derived fact a recorded provenance. The probe runs `dns → tcp → authentication → rtsp-negotiation → stream-open → first-frame → frames-received → codec → resolution → fps → stream-profile → latency → jitter`, times each stage individually, and emits **exactly one** mutually-exclusive `StreamProbeFailureCode`. Stages are selected per transport, with `skipped` distinguishing "this transport has no such step" from `not-executed`'s "the probe never got there" — so adding SRT or WebRTC is a new stage-set entry rather than a lifecycle change. Six supporting decisions: (1) **splitting DNS from TCP** is the highest-value change in the slice, because the two send an installer to a DNS server and a switch port respectively, and P-2 conflated both into "reachability"; (2) **the runtime names the failure and the console renders it** — P-2 derived the headline in the UI by scanning for the first failing check, which is inference in the visualization tier and would have drifted from the runtime the first time a stage was renamed; (3) **identity is appended to, never overwritten** (`CameraIdentityHistory`), because "when did this camera become a different device?" is unanswerable the moment a serial is overwritten in place; (4) **capability refreshes produce a severity-classified diff** — `minor`/`major`/`security`, where `major` is exactly the set that changes what analysis _costs or receives_, so a 1080p→4K jump is not buried beside a firmware string; (5) **cache freshness is computed on read, never stored** (`fresh`/`aging`/`expired`/`unknown`), because a stored freshness value is wrong the moment after it is written — the silent staleness the recommendation is about; (6) **timeline reason codes are required**, so a generic message is not merely discouraged but unwritable, and the credential-failure counter reads the typed code instead of pattern-matching prose that could be reworded upstream.
- **A correction the Architect's own diagram forced:** P-2's transition map required `configured → connected → monitoring`. The rec 7 diagram shows `Configured → Monitoring` directly, and it is right — a running analysis session **is** hardware evidence and can arrive without anyone pressing "test connection". Requiring a manual probe first would be the state machine disbelieving its own runtime. The evidence gate is untouched: `monitoring` still demands `hardware`.
- **A test-quality failure caught by the clock, not by an assertion:** the first staged implementation made the unit suite take **113 seconds**, because the new DNS and TCP stages were resolving and dialling `cam.local` for real. The seams existed but the tests were not using them. Fixed by injecting `resolve`/`connect` throughout (suite back to 7 ms) — and the slowness was the only signal, since every assertion still passed.
- **Alternatives Considered:** (a) keeping a single `reachability` stage — rejected, it is the conflation that sends installers to the wrong end of a building; (b) inferring the failure code in the console from the check list — rejected per rec 10, and it was the existing behaviour, so this is a removal not an omission; (c) storing `freshness` on write — rejected, it is a function of the clock and would be stale immediately; (d) diffing stream profiles positionally — rejected, devices reorder them between firmware versions and every upgrade would report every profile as changed, training operators to ignore the feature; (e) free-text timeline reasons with a parser — rejected, it is what the typed code replaces and the credential counter already depended on it; (f) an arbitrary `windowHours` for trends — rejected in favour of named windows, since the point is to _bound_ the view and `windowHours=100000` would quietly reinstate the lifetime average that hides last night.
- **Reason:** P-2 could say a camera was broken. It could not say what changed, when, or which step failed — and those are the three questions an operator actually opens the console with. Every addition here is an answer the platform already had in its possession and was discarding: the runtime knew which stage failed and returned prose; discovery read the device's UUID and dropped it; a capability refresh knew both the old and new values and reported neither.
- **Impact:** `@vip/contracts` **+3 → 140 generated schemas** (`stream-probe-check`, `capability-change`, `camera-identity-change`), plus additive fields and enums across camera: `StreamProbeFailureCode`, `CapabilityChange`(+severity), `CapabilityChangeSeverity`, `CameraIdentityChange`, `CameraIdentityHistory`, `IdentityAttribute`, `IdentityConfidence`, `TimelineReasonCode`, `HealthTrendWindow`, plus per-stage `durationMs`, `totalMs`, probe provenance and cache `source`/`freshness`. AI runtime: `stream_probe.py` rewritten as a staged pipeline with injected `resolve`/`connect` seams and `PROBE_VERSION`; `/streams/validate` echoes caller provenance and stamps runtime version. `services/camera`: new `domain/capability-diff.ts`; `domain/identity.ts` gains history/confidence/merge; `domain/capability-cache.ts` gains freshness; `domain/health-history.ts` gains `offlineCount`, `averageProbeMs` and named windows; `configured → monitoring` added to the transition map. ## ED-0049 — P-2.2 Operational Evidence: probe reports become evidence, not the latest reading

- **Date:** 2026-08-02 · **Phase:** Product phase (P-2.2) · **Architect direction:** P-2.1 acceptance ("Every probe execution should become immutable evidence"; "Never overwrite previous probe reports"; "Allow every probe to reference Previous Probe / Capability Snapshot / Identity Snapshot"; "Differentiate expected and unexpected drift"; "Compute a confidence score for operational health… independent from AI confidence"; "Replaying a probe report without re-contacting the camera"; "Maintain compatibility history… avoid presenting only the latest status"; "Track long-term averages"; "Preserve the staged probe pipeline as the universal validation engine"; "Do not redesign this subsystem") and the P-2.2 acceptance ("Rename Transport Registry to Validation Provider Registry"; "Maintain compatibility over time… Firmware, Runtime Version, ONVIF Version, Codec, Transport, Edge Profile"; "Do not base confidence on a single probe"; "Unify Identity / Capability / Probe / Compatibility History and Operational State into one chronological timeline"; "P-2.2 completes the operational evidence subsystem").
- **Decision:** Turn a probe from **the latest reading into a piece of evidence**. Probe reports move out of the overwritten `Camera.operational` field and into an append-only `camera_probes` collection, each record self-describing (probe id, per-camera `sequence`, timestamp, provider, probe version, runtime version, evidence class, correlation id, the configuration snapshot it ran against, the identity it ran against, and a backward pointer to the probe before it). Six supporting decisions: (1) the transport table becomes a **validation provider registry** — RTSP, HTTP, WebRTC, SRT, recorded video, DVR export, NVR playback, USB camera and edge stream all run the one staged pipeline, and a new source type is a registration rather than a code path; (2) **drift is classified, not listed** — codec/resolution/FPS/profile/security changes stay `unexpected` _even under a firmware upgrade_, because attributing them to the upgrade is how the one investigable event stops being investigated; (3) **operational confidence is never computed from a single probe**, guarded by two floors (≥2 hardware probes, or ≥3 _measured_ state changes) and issuing **no score at all** in the `insufficient-evidence` band; (4) **compatibility is a register keyed by (dimension, value)** across firmware, runtime version, ONVIF version, codec, provider and edge profile, where older rows are never overwritten and `unsupported` is earned only by a device-side failure under hardware evidence; (5) **replay is a pure function** over a stored record — no camera, network or probe port in scope, and a `GET` route, so it cannot drift into a re-measurement; (6) **metrics are derived on read, never accumulated**, so the number and the reports behind it can never disagree.
- **The architectural recommendation, and the decision taken on it:** the Architect recommended collapsing the four histories into a single `OperationalTimeline` and left the call to us. **Unify the reading; keep the writing separate.** The four records have different bounds (lifecycle 50 · identity 30 · probes 200 · compatibility 60), different keys (time · attribute · sequence · dimension-value) and different retention rules; one physical log forces one rule onto all four — either discarding immutable probe evidence to keep the timeline small, or letting a camera that reconnects every thirty seconds bury a firmware change under ten thousand identical rows. `GET /cameras/:id/evidence` merges them chronologically on read, costing one sort and creating no second copy of any fact. The archive is authoritative for probes, so the lifecycle's echo of an archived probe is dropped from the merge rather than double-counted.
- **Two defects the tests found, not review:** (a) **a timestamp is not a total order** — two probes in the same millisecond left the `previousProbeId` chain down to whatever the storage engine returned, fixed by a per-camera `sequence`; (b) **confidence was scored from one probe**, because a probe produces both a report _and_ the lifecycle transition it causes, so counting "observations" let a single probe look like two independent facts. Fixed by counting only _measured_ state changes and requiring two hardware probes.
- **A behaviour change worth naming:** a **simulated** or **USB** source no longer runs the DNS and TCP stages. Under the provider registry it has no network endpoint, so those stages are `skipped` — previously the probe resolved and dialled whatever host the URI happened to carry, which is both a report of work it had not done and the root cause of P-2.1's 113-second test suite.
- **Alternatives Considered:** (a) an unbounded probe array on the camera document — rejected, ~2 KB per report and a camera probed every five minutes outgrows a single record within the year; (b) unbounded retention in the archive — deferred rather than pretended: retention is bounded and **`evicted` makes the trimming self-declaring**, and durable long-term archival is an evidence-store decision, not a camera-service one; (c) a single physical `OperationalTimeline` — rejected above; (d) marking a firmware unsupported on any probe failure — rejected, a wrong password would brand a vendor's release unsupported across an estate after one bad afternoon; (e) letting a firmware upgrade explain a resolution drop — rejected, a regression under an upgrade is the finding, not the exception; (f) accumulating averages into stored counters — rejected, a stored average cannot be recomputed for a different window nor audited against the evidence it came from.
- **Reason:** every probe used to erase the one before it, which makes the most common operational question — _was it always like this?_ — permanently unanswerable. A camera taking four seconds to first frame is unremarkable if it always did and an incident if it took 300 ms last week, and only one of those readings survived.
- **Impact:** `@vip/contracts` **+9 → 149 generated schemas** (`camera-probe-record`, `camera-probe-history`, `probe-replay`, `camera-probe-metrics`, `compatibility-record`, `operational-confidence`, `camera-evidence-timeline`, `fleet-probe-metrics`, plus the P-2.1 three), with new `ValidationProvider`, `ProbeConfigurationSnapshot`, `ProbeComparison`, `CapabilityChangeDirection`/`CapabilityDriftCause`/`CapabilityDrift`, `CompatibilityDimension`/`CompatibilityStatus`, `OperationalConfidenceBand`, `CameraEvidenceSource`/`CameraEvidenceEntry`, and additive fields on `CapabilityChange`, `CameraTimelineEntry` (`durationMs`, `probeId`), `StreamProbeResult` (`provider`), `Camera` (`compatibility`, `probeCount`) and `CameraHealthSummary` (`confidence`). AI runtime: `stream_probe.py` gains the provider registry (`register_provider`/`resolve_provider`/`providers`), `PROBE_VERSION` → `3`, and `provider` on every report. `services/camera`: new `domain/probe-archive.ts`, `domain/compatibility.ts`, `domain/confidence.ts`, `domain/probe-metrics.ts`, `domain/evidence-timeline.ts`; `capability-diff.ts` gains drift classification; a second tenant-scoped collection (`camera_probes`, two indexes); five new routes (`GET /cameras/:id/probes`, `/probes/metrics`, `/probes/:probeId`, `/cameras/:id/evidence`, `GET /cameras/metrics`). Console: probe history + replay panel, drift badges, compatibility register. **Contracts 277 · Python 850 · camera 156 · console 76.** Docs: [ADR-0024 P-2.2 amendment](../adr/ADR-0024-camera-lifecycle-evidence-gate.md), [CONSTRAINTS §27–29](CONSTRAINTS.md), [P-2 tracker](../tracker/P-2-CAMERA-LIFECYCLE.md).

## ED-0050 — P-2.3 Chain of Custody: the Camera Foundation, explained and frozen

- **Date:** 2026-08-02 · **Phase:** Product phase (P-2.3, closing the Camera Foundation) · **Architect direction:** two overlapping P-2.2 acceptance messages ("Every evidence record should include stable evidenceId · evidenceClass · evidenceSource · producer · producerVersion · runtimeVersion · correlationId · sessionId · cameraId · tenantId · createdAt"; "The evidenceId must remain stable forever"; "Root-cause navigation should work in both directions"; "Treat multiple capability changes produced by the same observation as one logical change event"; "Persist only measurements, observations, evidence — never confidence, trends, health scores, summaries"; "Avoid SELECT * … prefer pagination, indexed sorting, bounded queries"; "The unified evidence timeline should become the single investigation API"; "Every automated operational decision should be explainable… this should not introduce any new runtime behavior"; "Explicitly freeze the Camera Foundation"; "Do not introduce any new services or runtime layers").
- **Decision:** Close the Camera Foundation by making every operational claim **traceable to immutable measured evidence**, and then freeze it. Seven parts: (1) a **chain-of-custody envelope** identical on every evidence item, with `evidenceId` **derived deterministically from the record it came from** — the timeline is merged from four stores on every request, and a generated id would make every navigation link dangle on the next refresh; (2) **bidirectional causation** — backwards answers _why did this happen_, forwards answers _what did it break_, which is what decides whether an incident is over and is unanswerable from a backward chain alone; (3) **capability changes grouped into one changeset**, because a firmware upgrade that moves the codec, the resolution, a profile and the frame rate is one upgrade with four consequences, and four rows at the same instant read as four problems; (4) **nothing derived is persisted** — confidence, trends, decisions and metrics are computed from the archive on every read, so a conclusion can never drift from the evidence behind it and an explanation improves retroactively; (5) **operational decision records that are reconstructions, not recordings** — `explainDecisions()` answers _why was this camera degraded / why was this probe marked failed / why did confidence drop_, each pointing at evidence ids that resolve in the timeline, and **no code path consults one**, which is what allows the feature inside the freeze; (6) **bounded, indexed, sampled-honestly fleet reads** — sorting and limiting moved into the query, the fleet aggregate counts cameras rather than loading them, and `sampled` says plainly when the caps bit; (7) the **freeze itself** (CONSTRAINTS §30–32).
- **A pre-existing violation named rather than quietly kept:** rule (4) says never persist a summary, and `Camera.health` is one — a coarse rollup stored since P1-4 for list views. It is recomputed from the latest measurement on every write and is never independently settable, but it is stored. Deriving it touches a read path shared with other services and is a P-3 change, not a P-2.3 one. Recorded here rather than left for someone to discover.
- **A defect the tests found:** P-2.2's timeline de-duplication dropped _any_ entry carrying an archived `probeId`. That silently deleted the **state changes those probes caused** — the exact causal link the timeline exists to show — and it only surfaced when a test asked for the causation chain. Only the `probe-succeeded`/`probe-failed` echo should be dropped.
- **Alternatives Considered:** (a) generated evidence ids — rejected, they cannot be linked to across a request boundary; (b) persisting decision records — rejected, it is a stored conclusion by definition and would freeze explanations at the version that wrote them; (c) an exhaustive `Record<CameraEvidenceSource, string>` in the console — rejected, it makes a future producer a compile error here and a blank cell in production, so labels are lookups with a fallback and a test renders a source the console has never heard of; (d) declaring the future evidence sources when their producers ship — rejected, adding an enum value later is the one contract change that is not purely additive for a strict parser, so `diagnostics`/`recovery`/`certification`/`session` are declared now; (e) a full-collection fleet aggregate — rejected as a denial of service at a hundred thousand cameras, and the bound is disclosed rather than hidden.
- **Reason:** the foundation could already prove what it measured; it could not yet **explain itself**. An operator asking "why is this camera degraded?" got a state and a timestamp, not the rule that ran and the evidence it ran on — and an unexplained refusal to change state looks exactly like a bug to whoever is watching it not move.
- **Impact:** `@vip/contracts` **+5 → 154 generated schemas** (`camera-evidence-entry`, `confidence-trend`, `capability-change-set`, `operational-decision`, `camera-decision-log`), with new `EvidenceType`, `EvidenceProducer`, `EvidenceLinks`, `ConfidencePoint`, `OperationalDecisionKind`, `DecisionActor`, four additional `CameraEvidenceSource` values, and additive fields on `CameraProbeRecord` (`supersedes`), `CameraTimelineEntry` (`changeSetId`), `CapabilityRefreshResult` (`changeSet`) and `FleetProbeMetrics` (`sampled`). `@vip/tenancy`: `findMany` gained `sort`/`limit`/`skip`. `services/camera`: new `domain/decisions.ts`; `evidence-timeline.ts` rewritten with provenance and link resolution; `confidence.ts` gained `confidenceTrend`; bounded archive queries throughout; two new routes (`GET /cameras/:id/confidence`, `/cameras/:id/decisions`). Console: `EvidenceTimelinePanel` rendering generically from the envelope, with the decision explainer behind it. **Contracts 277 · Python 850 · camera 171 · console 79.** Docs: [ADR-0024 P-2.3 amendment](../adr/ADR-0024-camera-lifecycle-evidence-gate.md), [CONSTRAINTS §30–32](CONSTRAINTS.md), [P-2 tracker](../tracker/P-2-CAMERA-LIFECYCLE.md).

## ED-0052 — P-3 Organization Hierarchy: the customer's physical world, traversed by the backend

- **Date:** 2026-08-02 · **Phase:** Product phase (P-3, the first product slice) · **Architect direction:** P-3 approval ("This is the Product Layer built on top of the frozen Camera Foundation v1.0. Continue with the current architecture and do not redesign any of the frozen foundations"; "The backend should own hierarchy traversal — return locationPath / breadcrumb information directly from APIs. The frontend should never reconstruct hierarchy by walking parent nodes"; "Never permanently delete hierarchy nodes… historical evidence, investigations and audit logs must always resolve correctly even after organizational restructuring"; "Never use display names as identifiers"; "Avoid recursive hierarchy traversal during normal operations… no O(n²) hierarchy walks"; "ensure nothing in the hierarchy assumes cameras are the only physical objects"; "No console logic should derive business rules. The backend remains the source of truth").

- **What the slice was actually for.** P1-1 built `OrgNode` — eight types, a materialized ancestry, tenant-scoped — and then nothing consumed it. A tenant got an `org` root at provisioning and never gained a second node; the console hardcoded `zoneId = 'on_default'`, named in a comment so it would not become a silent assumption. The model existed; the product did not. P-3 is the first slice a customer sees as _theirs_, and the backbone every later module attaches to.

- **The decision that shaped the rest: traversal is owned by the backend.** `OrgLocation` carries `breadcrumb`, `depth`, `label`, `allowedChildTypes` and `hasChildren`, all derived on read and none of them stored. The immediate consequence is that the console's "add a location" menu offers exactly what the server said is permitted, so the page contains **no containment rule at all** — and the alternative is not hypothetical. P-2 derived the probe-failure headline in the console by scanning for the first failing check; that is business logic in the visualization tier, and it would have disagreed with the runtime the first time a stage was renamed. Removing it was a deletion, not a feature. Serving derived reads costs one join the server was already positioned to do and removes an entire category of drift.

- **Containment: enforced, skippable, never invertible.** A node may sit under any _strictly outer_ type. `org → site → zone` is a valid three-level estate for a customer with one building; `floor → region` is not a hierarchy at all. Requiring all eight levels would make the model unusable for the small customer; allowing inversion would make "everything under this site" unanswerable. **This narrows an endpoint that previously accepted anything** — P1-1 validated only that an `org` had no parent and a non-`org` had one, so a zone could contain a region. Recorded as a bug fix that makes the code match documented behaviour (which the freeze permits without ceremony) rather than slipped in unremarked, because it does change what an existing route accepts.

- **Archive, never delete — and no route at all.** Evidence, incidents and audit records reference locations by id for as long as they are retained. A delete turns a two-year-old investigation into a dangling id at the exact moment someone needs to read it. Archiving cascades to the subtree, leaves the working views clean, and keeps every historical reference resolving — breadcrumb included, which is precisely when an operator most needs to know where something _used to be_. There is deliberately no `DELETE` route: a route that exists and is discouraged is a route that gets called, so its absence is the guarantee and a test asserts the 404.

- **The boundary held under pressure.** "Every camera under this site" is the obvious feature and the obvious way to build it is a call from the camera context into the tenant context to resolve the subtree — which is how a distributed monolith starts ([PLATFORM_BOUNDARIES](../architecture/PLATFORM_BOUNDARIES.md) rule 4). Instead the subtree resolves where the tree lives and arrives at the inventory as a **set of zone ids**: a filter, not a hierarchy. The Camera Service still does not know what a site is. Denormalising ancestry onto each camera was also rejected — a second copy of another context's fact, wrong from the instant a site is renamed, and re-derivable only by a fan-out write across the inventory to serve a read that already had an answer.

- **Nothing recursive touches the store.** Ancestry is multikey-indexed (`tenant_path`) and depth is indexed (`tenant_depth`), so a subtree is one lookup at any depth, a page of resolved locations costs three queries regardless of estate size, and the tree is a single pass. A 5,000-node estate assembled in one pass is a test, not an aspiration — and the assertion that matters is not the elapsed time but that the work is single-pass, because an accidental per-node parent walk would be O(n·depth) and would surface only as a suite that quietly got slower. That is the same signal that caught the runtime dialling real hostnames in AI-5.

- **A move is one bulk write.** Rewriting a subtree as N awaited `updateOne` calls is N round trips and, worse, N chances to be interrupted halfway and leave the tree describing two different shapes at once. `movedPaths` returns the rewrites as **data** — which is what makes the arithmetic testable without a store, and what a future bulk move would call.

- **`id` is identity; `name` is a label.** Every reference in the platform is by id, so a rename touches one document and nothing else — which is what makes renaming safe enough to expose as a one-click action, and why the label appears updated everywhere immediately (it is derived, never stored). `type` is immutable and has no field in `UpdateOrgNodeInput`: a floor becoming a region reinterprets every record that referenced it, and getting it wrong should mean creating the right node and moving the children, an operation whose cost is visible.

- **The one recommendation declined, and why.** The Architect asked for `displayName` alongside an immutable id. The _substance_ — immutable ids, editable labels, references by id only — is implemented and tested. The **field** is not: `name` already is the display label and is documented as such, and adding a second field meaning the same thing is exactly the "one shape in two places" that Foundation Principle 5 exists to prevent. Two fields that must always agree eventually do not.

- **The hierarchy holds no occupancy count.** `OrgTreeNode` deliberately has no `cameraCount`, and a contract test asserts none of `cameraCount`/`cameras`/`deviceCount`/`assetCount` can appear. It would be both a second copy of another context's fact and a standing assumption that cameras are the only occupant — and the estate will hold NVRs, door controllers, readers, alarm panels, sensors and barriers. The hierarchy describes _places_; it does not know what stands in them.

- **Two defects the tests found, not review:** (a) **a subtree read reported its own root as an orphan** — `under=X` returned everything beneath X but not X, so the top node's parent was legitimately absent and `buildTree` classified it as an inconsistency; fixed by including the node itself and letting the caller declare it a root, which keeps "the parent is missing" meaning _inconsistent_ rather than _you asked for less_. (b) **A Radix `Select` cannot be opened in jsdom** (`hasPointerCapture` is unimplemented), which would have meant the location picker — the one control that decides where a camera goes — was untestable; shimmed in `test/setup.ts` rather than routed around.

- **Governance opened alongside the code**, per the P-2.3 acceptance: [PRODUCT_PRINCIPLES](PRODUCT_PRINCIPLES.md) (the product equivalent of FOUNDATION_PRINCIPLES, under one test — _can a customer understand the value of this in a demonstration?_) and [PLATFORM_ROADMAP](PLATFORM_ROADMAP.md) (Foundation ✅ → Product → Business → Solution; governance only, authorising nothing). CONSTRAINTS **§35–38**.

- **Documented, not built** (extension points, so the milestone that needs one extends a known shape rather than inventing a parallel one): inherited permissions · bulk import and bulk move/archive · location templates · audit trail · localisation · non-camera assets. See [ADR-0025](../adr/ADR-0025-organization-hierarchy.md).

## ED-0053 — P-3 acceptance hardening: proving the Location Hierarchy rather than asserting it

- **Date:** 2026-08-02 · **Phase:** Product phase (P-3 acceptance hardening) · **Architect direction:** P-3 approval + hardening approval ("This is a foundation-hardening and governance slice, not a feature slice… the objective is to prove that the hierarchy foundation is complete, scalable, future-proof, and ready to be frozen"; "Do not merely verify indexes exist — prove they actually satisfy expected production queries. The important question is _will MongoDB actually use these indexes efficiently?_ rather than _did we create indexes?_"; "Add a structural test proving the hierarchy implementation never introduces recursive traversal"; "Verify historical evidence remains attached to historical locations"; "Document the invariants that define the hierarchy… these are architectural laws"; "Before freezing P-3, verify P-4 can consume the hierarchy without changing hierarchy contracts"; "Freeze Hierarchy Foundation v1.0").

- **The distinction that produced everything else.** The Architect drew a line between _"we created indexes"_ and _"the planner will use them"_, and asked for the second. Those turn out to be very different claims. Making the second one checkable meant declaring index specifications as **data** (`adapters/indexes.ts`) and writing a model of how the planner actually decides — equality keys must occupy a contiguous index prefix, and the **sort key must be the next key**. Every read the two services issue is then checked against it.

- **Three defects, none caught by review, none visible in a test fixture.** (a) `tenant_zone` was `{tenantId, zoneId}` while the P-3 location filter sorts by `_id` for its cursor: the filter was index-served and the sort was not, so MongoDB gathered every camera in the subtree to order it in memory — correct on four rows, a blocking sort against the 32 MB limit on a million-camera estate. (b) The **subtree tree read** filters on `path` and orders by `depth`; `tenant_path` cannot serve that sort, so a 100,000-node subtree was being sorted to return 5,000 rows. (c) The **unfiltered paged camera listing** — the simplest query an operator can issue — had no covering index at all. Fixed by adding `_id` to `tenant_zone`, and by adding `tenant_path_depth` and `tenant_cursor`. Every index now ends in the cursor key, and a test asserts it.

- **The model had to be built honestly or it would have found nothing.** Two early versions were wrong in the direction that makes a coverage check worthless: one treated "the sort field is also filtered" as sufficient (which would have declared defect (b) covered), and one refused `findOne({tenantId, _id})` because `tenantId` is not in the `_id_` index (which would have demanded an index the planner would ignore). The fixes were to require the sort key to be **exactly next**, and to model a fully-consumed **unique** index as covering with residual predicates free. A coverage check that wants to pass is worse than none, because it converts an open question into a false answer.

- **Depth is bounded by containment, not by convention** — the answer to "prove traversal never recurses unboundedly". `canContain` requires the parent's rank to be strictly lower than the child's, so any root-to-leaf chain has strictly increasing ranks drawn from eight values and **cannot exceed eight nodes**. No import, customer or bug can produce a deeper one. That is what makes the depth-recursive helpers safe rather than a stack overflow waiting for a large estate — a hierarchy without that rule would need every walk rewritten iteratively. Also asserted: no exported hierarchy function is `async` or contains an `await`, so a per-node read cannot be introduced accidentally.

- **The one requirement that is not met, stated as such.** Evidence recorded while a camera sat in Zone A resolves to **Zone B** after the camera moves. Every reference survives — renames, moves, archives and restores change no id, so no investigation link ever dangles — but the _answer changes_, which for an investigation is worse than an error because nothing signals that it did. Neither half of the cause is in the hierarchy: a camera's `zoneId` is mutable and evidence references the _camera_; and a location's ancestry is current rather than historical. The fix is to freeze `zoneId` and its `path` **on the evidence record at write time**, exactly as `CameraProbeRecord` already freezes a configuration snapshot — an additive **Evidence-context** change requiring no change to anything frozen here. Implementing it was out of scope for a slice whose brief was explicitly "do not introduce new runtime behavior", so it is carried forward and the test asserting today's behaviour is written so that **fixing it makes the test fail**, forcing it to be rewritten as the guarantee rather than passing either way.

- **Twelve invariants, each asserted rather than described.** One parent · no cycles · valid path · correct depth · depth bounded at 7 · immutable id and type · editable name · containment preserved · backend-owned traversal · no deletion · occupant independence · tenant isolation. Move integrity is checked at **every level** — zone, floor, building, site, branch, country, region — plus a chain of moves and a 10,000-node subtree move, each verifying ancestry, breadcrumbs, materialized paths, descendants and references against one another and against the rebuilt tree.

- **Scale, and the operational consequence.** A 101,001-node single-tenant estate builds in one pass; growth is confirmed linear by comparing 5k against 20k (linear ≈ 4×, quadratic ≈ 16×); breadcrumb resolution costs `path.length` map lookups **independent of estate size**. The consequence worth recording is not the numbers but the access pattern: past the 5,000-node tree ceiling the whole-estate read is **not** the path — reads become subtree- or search-scoped, both bounded and both indexed, and the tree read reports `truncated: true` rather than returning a partial estate that claims to be whole.

- **Verified and deliberately not built:** six future query verbs answerable from indexed fields already stored; additive metadata and external references (a today-reader parses a tomorrow-record); asset neutrality (no occupancy field, no device word, any occupant attaches by reference); bulk import giving byte-identical validation from CSV, Excel, ERP, AD, REST or HR at 10,000 rows with no store access; and **P-4 readiness** — a rule scopes to a node id and resolves its zones with one indexed predicate, needing no hierarchy contract change.

- **A recommendation adopted in documentation only.** The subsystem is now called the **Location Hierarchy**, because it models the physical world rather than organizational ownership. The code keeps `OrgNode`, `OrgNodeType` and `/org-nodes`: renaming published contracts and routes is precisely the change the freeze forbids without an ADR, and clarity of prose does not buy a breaking change. The console already says "Locations" everywhere a customer can see.

- **Frozen.** Location Hierarchy v1.0 — additive-only, breaking changes by ADR — declared in `FOUNDATIONS` and recorded in [HIERARCHY_FOUNDATION_V1](../architecture/HIERARCHY_FOUNDATION_V1.md). The first **product-layer** subsystem to receive foundation governance, for the same reason the foundations got it: everything else attaches to it. CONSTRAINTS **§39–40**.

- **Documentation only.** No source file changed, no test changed, no behaviour changed. The slice's whole output is governance — which is the correct output for a freeze, because a frozen subsystem that nobody can navigate is frozen in the unhelpful sense.

- **The observation became an owned work item.** The historical-location defect found in the previous slice is now **[E-1](../tracker/E-1-EVIDENCE-LOCATION-SNAPSHOT.md)**, owned by the **Evidence context**, registered as [TD-20](../../tracking/TECH-DEBT.md), with acceptance criteria and an explicit statement that no `Org*` contract may change to fix it. Three decisions inside it are worth recording rather than leaving to whoever picks it up: (a) **do not store a hierarchy version** — a version identifies a shape, not a state, and would not tell a reader what the ancestry _was_, which is the entire question the `path` snapshot answers exactly; (b) **do not backfill** — there is no correct value to invent, and writing today's ancestry onto old records would convert a detectable gap into an undetectable one permanently; (c) **render "location not captured"** for pre-E-1 records, because a record that cannot answer the question should say so rather than answer it wrongly.

- **The index policy exists because the rule is counter-intuitive.** [INDEX_POLICY](INDEX_POLICY.md) records **equality → sort → range**, and the specific thing that catches people: an index that stops at the filter key serves the filter and _abandons the sort_, which on a fixture is instant and on a million rows is a blocking sort against the 32 MB limit. It also records when **not** to index — a speculative index is write cost bought against a guess, and an unanchored substring regex will not use a B-tree however much one wishes it would. The multikey note is the one a future reader will need: `{tenantId, path, _id}` writes one index entry _per ancestor_, which is affordable only because containment bounds depth at 7. An unbounded hierarchy would make that index unbounded per document.

- **Performance budgets are stated as budgets, and one is stated as "not interactive".** A 10,000-node subtree move is correct, atomic in one write and tested — and it is a reorganisation of a customer's estate, not a click. Calling it a maintenance operation in the budget table is how it avoids ending up behind a spinner with no progress and no cancel. Substring search is deliberately left **unbudgeted**: giving a number to work that is O(tenant nodes) would imply an index that does not exist.

- **The benchmark section is written to reduce what the numbers claim, not to sell them.** The 101,001-node figure comes from a deterministic unit test over uniform synthetic data on unpinned hardware, with no serialization, no concurrency, no disk and — the important one — **no MongoDB**. No query plan was captured and no `explain()` was run: index coverage is proven against a _model_ of the planner's rules, which is a materially weaker claim than a measured plan, and the document now says so. Nothing about 1,000,000 cameras was measured; that is a reviewed design target. The scale assertions were deliberately given generous absolute bounds because they exist to catch an accidental O(n²), not to benchmark a host — a tight bound would fail on a loaded CI machine and teach everyone to ignore it. Before any performance claim reaches a customer it needs the AI-5a harness, with a pinned fingerprint and a baseline comparison (§23).

- **Two permanent rules added.** **§41** — public contracts are frozen while documentation terminology is free to improve; cosmetic API renames are forbidden, because a rename breaks every consumer, every stored document and every integration in exchange for a clearer word. **§42 / [Foundation Principle 11](FOUNDATION_PRINCIPLES.md)** — every foundation change answers the three migration questions before it is written. The pattern already in the code is the illustration: `OrgNodeDoc.status`, `depth` and `archivedAt` are optional **on read** and written on every new record, so a document written before P-3 is an active node rather than an invalid one. That is what additive means in a _store_, as opposed to in a schema — a distinction that only shows up when a real deployment upgrades.

- **[FOUNDATIONS](FOUNDATIONS.md) is now the canonical register** — six foundations, what each owns, what "frozen" means uniformly, the three migration questions, and a table of **known limitations carried across foundations** so they are found rather than discovered. That last table is the part likely to matter most in a year.

- **Documentation status labels** (**Implemented · Future Extension · Out of Scope · Known Limitation · Technical Debt**) are now a Definition-of-Done item, with two rules that carry the weight: a Known Limitation must name its owner and its tracker, and a Future Extension must not be written in the present tense. "The hierarchy supports inherited permissions" is false; "a permission grant would attach to a node id" is true and visibly a plan. The two read identically to a hurried reader, which is how a roadmap becomes a promise.

- **The P-4 guardrail is written down before P-4 starts**, which is the only time it is worth writing: P-4 consumes the Location Hierarchy exactly as it exists, and any contract modification needs an ADR, architectural review and approval — none of the three optional. Already verified: a rule scopes to a node id and resolves its zones with one indexed predicate, needing no hierarchy field, contract or route that does not exist.

## ED-0055 — P-4 Rule Designer: rules learn where they apply, and why they did not fire

- **Date:** 2026-08-03 · **Phase:** Product Capability layer (P-4) · **Architect direction:** P-4 authorization ("The architecture is no longer the product. The product now consumes the architecture"; "Rule Designer must consume Platform Core, AI Runtime, Operational Runtime, Camera Foundation, Evidence Foundation, Location Hierarchy — no bypasses, no duplicate logic"; "The Rule Designer should produce configuration. It must never generate application code"; "Design Rule Definitions as immutable — editing creates a new version; historical alerts continue pointing to the version that generated them"; "Before activation verify referenced cameras/zones/behaviors/composites/schedules/outputs exist — validation must fail before deployment"; "Never design opaque rule execution"; "Rules should naturally scope by Organization → … → Zone → Camera using the existing hierarchy"; "Avoid per-event database queries. Prefer compiled rule evaluation over repeated lookups"; and the 70/20/10 priority shift toward customer-facing capability).

- **What was already there, and what was actually missing.** P1-7 had built a good engine: a sandboxed predicate tree, five lifecycle states, immutable version records with full snapshots, and a dry-run. Three gaps remained, and all three are why P-4 follows P-3. A rule had **no location** — every rule applied to the whole tenant, so a customer with forty sites could not say "loitering matters at the London docks and nowhere else", which is the first thing any of them asks. **Nothing validated a rule before it went live**: `validated` was a state an author could select with no check behind it. And **explainability was three booleans** — "condition did not match" starts an investigation rather than ending one.

- **The decision everything else followed from: scope is authored as nodes and evaluated as a set.** A rule names hierarchy nodes at any level; the expansion to leaf zone ids is computed at validation and **stored on the immutable version**. Two reasons that point the same way. Evaluation must not query — the engine sees every event and evaluates every enabled rule, so a hierarchy lookup there is a query per rule per event, and a `Set.has` is not. And a version must mean one thing forever: the expansion travels with the version, so an incident raised six months ago can be shown the exact zones its rule covered _then_. Recomputing on read would silently rewrite the past, which is precisely the failure [E-1](../tracker/E-1-EVIDENCE-LOCATION-SNAPSHOT.md) records for evidence. **The cost — staleness when zones are added beneath a scoped node — is accepted deliberately** and made visible (`resolvedAt`, and the console says so), because the alternative trades a visible, correctable staleness for an invisible rewriting of history.

- **The alternative I most wanted to take, and why I did not.** Carrying the zone's **ancestry on the `EventEnvelope`** would let a rule match `path.includes(nodeId)` with no expansion, no port, and no staleness at all. It is the cleaner design on paper. It fails because the producers — camera, media, inference — do not know the hierarchy either, so the ancestry would have to be resolved cross-context at **event-write** time: the same call, moved to a hotter path and multiplied by every event rather than every validation. Recorded in ADR-0026 so the next person who has the same good idea finds the reason it was declined.

- **A bounded, recorded exception to boundary rule 4.** The rules service reaches the hierarchy through a **port**, defaulting to unavailable, called at validation and enablement and **never per event** — the engine's hot path holds a pre-expanded set and could not reach a hierarchy if it wanted to. Rule 4 exists to prevent a synchronous cross-context call in a _runtime_ path, which is how a distributed monolith starts; a validation-time call that fails closed and whose result is snapshotted onto an immutable version is a different shape with different consequences. Named in the ADR the way ADR-0023 named discovery, rather than left to be discovered.

- **"A check that could not run is not a check that passed."** `RuleValidationReport` carries `valid` and `verified` as separate fields, and a rule cannot be enabled on an unverified check. Letting one go live because a check was skipped is the configuration version of certifying hardware from a simulation — the exact failure Foundation Principle 3 exists to prevent, and the reason the ports default to _unavailable_ rather than to _fine_. The requirement is **proportional**: a tenant-wide rule references no location, so it validates fully with no hierarchy reachable, and demanding otherwise would block a small customer on a service they do not use.

- **Three failure directions chosen deliberately, all toward the visible one.** A **scoped rule with no expansion matches nothing**, not everything — treating an absent expansion as tenant-wide would put a rule for one site across the entire estate, failing open, silently, against the one thing the customer explicitly configured. An **event with no location fails a narrowed scope**, because treating "unknown" as "inside" is the same failure by another route. And **re-scoping drops the expansion**, so a stale expansion can never outlive the scope it belonged to. In each case the quiet rule gets noticed and its explanation names the cause; the rule firing everywhere looks like the product working.

- **Enabling and resolving are one operation**, in one version bump — I initially wrote them as two and caught it before tests: a scoped rule would have gone live with no expansion, which under the old fail-open compile would have matched the whole estate. That near-miss is why `compileScope` now fails closed _and_ why the gate resolves inline.

- **Explanations reuse the interpreter rather than re-implementing it.** `explainCondition` walks the same tree with the same `evaluatePredicate` the engine calls, and a test asserts the two agree on every node — two interpreters would drift, and an explanation that describes a decision the engine did not make is worse than none because it is believed. The **first** failing stage decides the summary: a rule scoped to the wrong site _and_ with a failing condition reports the scope, because fixing the condition would not have helped. Composites are short-circuited when evaluating and deliberately **not** when explaining, since the leaf that would have failed next is usually what the author needs. Explanations are derived, never stored (Principle 2).

- **TD-7's second half is paid down.** The engine no longer issues a `listEnabled` query per event: rules are compiled per tenant — sorted, bounded, scopes expanded — behind a TTL'd cache. Correctness is bounded by the **TTL, not by invalidation alone**, because a cache invalidated only on local writes is wrong whenever the write happened on another replica. Concurrent misses are coalesced, so a cold tenant hit by a burst issues one query rather than hundreds — the per-event query otherwise reappears exactly when load is highest. The test counts store calls across 1,000 events and asserts **one**; a test asserting the right incidents come out would have passed either way.

- **A pre-existing defect found, proven pre-existing, and not papered over.** Building the end-to-end "save the scope" console test surfaced that **the rule editor cannot be saved in edit mode at all** — its lifecycle and severity `Select`s fail form validation, so the PATCH never fires. I stashed the P-4 changes and reproduced it against the original editor before concluding anything: it predates P-4 and became merely _observable_ now, because P-3's jsdom `hasPointerCapture` shim lets Radix Select content mount in tests. Rather than assert a passing test I could not honestly make pass, the end-to-end save test was replaced with a direct test of the form↔contract mapping — which is where the P-4 logic actually lives and is unaffected — and the defect is registered as [TD-21](../../tracking/TECH-DEBT.md) with "reproduce in a browser first" as step one. It may be a jsdom artifact; either answer matters, and guessing helps nobody.

- **The freeze held.** P-4 consumed the Location Hierarchy through its published contracts and **changed no hierarchy contract, route or index** — the thing the P-3 freeze was for, tested by the first product slice to depend on it. Rules stayed declarative configuration (§43), no industry noun entered the model, and no new service or runtime layer was introduced.

## ED-0056 — P-4.1 Rule Operations: derive the diagnostics, gate the live edit, and three defects the exercise found

- **Date:** 2026-08-03 · **Phase:** Product Capability layer (P-4.1) · **Architect direction:** P-4 approval + 15 recommendations (compilation metadata · dependency graph · runtime metrics · evaluation budget · warm-up · structured explainability · instant rollback · cache observability · simulation API · import/export · tenant isolation · audit trail · performance benchmarks · immutable packages · P-5 readiness), closing with "these are just my suggestions, please choose best possible approach".

- **The framing that decided most of it.** Almost every recommendation is **operational** — things a support engineer, an operator or a deployment needs — and none of them may touch how a rule decides. So the whole slice is additive and inert: nothing added is read during evaluation, and the ADR says so in the contract comments as well as the prose, because the drift risk here is someone later reaching for a convenient hash in a matching path.

- **Diagnostics are derived, never stored.** Every fingerprint, dependency graph, complexity measurement and audit entry is computed from the rule and its versions on demand. A hash persisted beside the thing it describes can end up disagreeing with it after a migration or a restore, and a fingerprint that can lie is worse than none because it is trusted; recomputing costs microseconds and _is_ the verification. This is Foundation Principle 2 applied to metadata.

- **The audit trail was already there — it just did not read like one.** The Architect asked for a lifecycle trail (created · validated · compiled · activated · paused · rolled back · archived · restored). The platform has written an immutable `RuleVersionRecord` with a full snapshot since P1-7, and every one of those actions is already implied by it. Writing a parallel collection would create **two records of one truth**, written by different code paths, which eventually disagree with no principled way to decide which lied. Deriving instead also means the timeline works **retroactively**, on rules authored long before anyone thought about audit actions. `rolled-back` is derived the same way — a version whose content hash equals an earlier version's _is_ a return to that version — so it is detected however it happened, through the endpoint, a script, or an operator re-pasting an old body. An intent flag would have recorded only the first. I did not extend `RuleVersionRecord.changeKind`, which would have been a second non-additive enum change for less.

- **The content hash excludes `lifecycle`, and that is the design.** Lifecycle is operational state, not content: a rule paused overnight and resumed is the same rule. Folding them together makes both questions unanswerable — "was this edited?" would be true after a pause, and a genuine rollback would be unrecognisable, because disable-then-enable restores an earlier hash while changing nothing at all.

- **Defect 1 — editing an enabled rule bypassed the activation gate entirely.** P-4 gated `patch.lifecycle === 'enabled' && current.lifecycle !== 'enabled'` — the _transition_. So re-scoping a **live** rule to a deleted zone was accepted, and because re-scoping drops the expansion by design, the rule went `unresolved` and **matched nothing**. A live rule silently stopped firing and nothing in the product said so. The transition was never the dangerous moment; putting unvalidated content in front of live events is, however it got there. The gate now fires whenever a request leaves a rule enabled with changed content — and deliberately does not when the request leaves it not-enabled, so an operator can always fix-and-park a broken rule in one call. Now CONSTRAINTS §47.

- **Defect 2 — Mongo `$set` never removed a field the domain had deleted.** `applyUpdate` deletes `resolvedScope` on a re-scope precisely so the engine stops matching the zones the author just removed; `$set` with an object lacking that key leaves the stored value untouched, so the **old expansion stayed in the database and the rule kept firing on the old zones**. Fixed with a paired `$unset`. Defects 1 and 2 share a shape worth naming: correct domain behaviour defeated by the layer underneath it — the domain dropped the expansion and the store put it back; the domain required validation and the caller found the path that skipped it. Now CONSTRAINTS §48.

- **Defect 3 — a deeply nested body crashed the handler.** `RuleCondition` is a recursive Zod schema, so a deeply nested body overflows the stack **inside the parser** — before validation, before the budget check, before anything could report it, reachable by any authenticated author. Fixed with an iterative depth guard on the raw body. I verified it by disabling the guard and watching the test fail, rather than trusting that the guard was guarding something. Now CONSTRAINTS §49.

- **Statistics that cost nothing per event.** The obvious API — `record(tenantId, ruleId, …)` — puts two hash lookups per rule per event into the one loop this architecture exists to keep empty. Instead the registry hands out **counter objects**, resolved once at compile time and carried on the compiled rule, so the engine increments a field it already holds. The registry owns them so they survive recompilation; on the compiled set every number would reset every TTL and mean nothing. Timing is taken only past the scope check, because a rule the scope rejected did no work worth measuring. They are **per node** and say so: cluster totals are what the Prometheus counters are for, and summing these across a load balancer would produce a number wrong in a way nobody could detect. A node that is not evaluating returns **501**, not zeroes — an unstarted engine and an idle one produce identical zeroes and only one is worth paging about. Now CONSTRAINTS §50.

- **Rollback restores content, not state, and cannot go through `update`.** `UpdateRuleInput` cannot express absence — a patch omitting `condition` leaves the existing one — so a patch-based rollback yields a rule that is the union of two versions and identical to neither, the worst outcome for a feature whose promise is "put it back the way it was". Hence a separate `RuleStore.restore`. Lifecycle is deliberately not restored. Rollback is **instant when the rule is not live** (the target version carries its own expansion), and a **live** rule goes through the gate above — a considered divergence from "rollback must never require recompilation", because restoring content last verified an unknown time ago against an estate that has changed since is exactly what the gate is for, and "it used to work" is not a check.

- **Half a simulation, honestly.** Supplied-event simulation is implemented, because it is a dry-run over a list and there is no honest reason to stub something already achievable. Replay over stored history returns **501**: the event archive belongs to another context and reaching into it deserves its own design rather than arriving under a rule feature. Both shapes are frozen now so neither becomes a breaking change — which is what the recommendation was actually asking for.

- **Imports always land as drafts.** A package is a file, and a file arrives from somewhere; activating rules that arrived from somewhere is how an estate starts alerting on a configuration nobody in the room chose. Each imported rule returns with its validation report, so the references that did not survive the journey — a node id means one place in the source tenant and nothing in the target — are visible before anyone enables it.

- **One deliberate enum extension, recorded rather than smuggled.** `RuleReferenceKind` gained `condition`: the budget checks are about the rule's own predicate tree, which is not a reference to anything and had no honest home among the existing values. P-4 declared that set ahead of use _specifically_ to avoid this, and the exercise missed one. Squeezing it into `action` would have made every over-budget condition report the wrong subject.

- **Benchmarks record a baseline; gates assert a shape.** The scale harness (100/500/1,000/5,000 rules) shows per-rule cost flat at 81.7 → 85.6 ns and 5,000 rules compiling in ~2.5 ms. Those are a comparison point on one machine, never thresholds — so the regression gate asserts the **ratio** (cost per rule stays flat as the count grows), which a loaded CI runner does not move and a quadratic regression cannot pass. Same discipline the P-3 close-out asked for. Now CONSTRAINTS §51.

- **P-5 readiness, and the one gap named rather than hidden.** Rule ids, versions, scope snapshots, evaluation traces, dependency graphs, metrics, audit trail and compilation metadata are all reachable without changing the Rule Designer. The one thing P-5 will want and cannot have yet is an explanation for an incident that **already happened**: explanations are derived from an event, and the candidate carries the triggering event's id rather than the event. Reconstructing one means fetching from the Events context — a P-5 decision about how the investigation workspace reaches other contexts, not a Rule Designer gap. Recorded so it is a decision rather than a surprise.

## ED-0057 — P-4.2 Rule Support Surface: compose the artifact, refuse to score what was not checked, and validate P-5 before starting it

- **Date:** 2026-08-03 · **Phase:** Product Capability layer (P-4.2) · **Architect direction:** P-4.1 approval + 15 recommendations (immutable diagnostic package · rule health score · complexity classification · dependency health · package signature · difference viewer · statistics history · import validation report · operations API separation · artifact lifecycle · package compatibility · incident integration contract · diagnostic search · rule archive export · P-5 readiness verification), closing with a required **architecture validation pass** before P-5 and "these are my recommendations only please follow best approach as per your knowledge".

- **The framing.** P-4.1 built the diagnostic _pieces_; these ask for the _artifact_. The pieces were all there and had to be gathered by hand from six endpoints — which is exactly the work nobody does at 2 a.m., so in practice the diagnostics existed and were not used. Everything added is still derived, still operational, still unread during evaluation.

- **A score that can be taken apart, or no score at all.** `RuleHealth` reports a status, a 0–100 number and **the findings whose deductions sum to `100 − score`**, with the number computed _from_ the list so the two cannot disagree. The failure this avoids is specific and common: a rule sits at 78, everyone learns 78 is normal, and a real problem hides behind it. And where validation could not verify its references, the status is **`unknown`** and no score is offered — §44 one layer up. A `0/100` beside "cannot be checked" reads as "this rule is broken", which is a different and wrong claim. Now CONSTRAINTS §52.

- **The artifact omits what it does not know.** `RuleDiagnosticPackage` leaves the runtime sections **absent**, not zeroed, on a node that does not evaluate — zeroes and "no data" are different facts and only one is worth acting on. It also carries **no explanation trace**: an explanation is per-event and a rule has no event, so the condition _structure_ is included and a trace is a `simulate` call away. Synthesising one would have made the artifact's most-read section its least trustworthy. Now CONSTRAINTS §53.

- **Complexity is relative, and bands on the worst dimension.** "40 condition nodes" means nothing to an operator who does not carry the ceiling in their head, so the classification is a function of the measurement **and** the deployment's limits — a rule is complex with respect to something, and the band moves when the ceilings move. It bands on the **worst** dimension rather than an average, because a rule with one leaf condition and 4,900 covered zones is not simple and averaging says it is.

- **`unknown` is a real dependency status.** Dependency health is opt-in (`?status=true`) because checking calls other contexts, and anything the platform cannot answer for is `unknown`, never `resolved` — "nothing is broken" and "nobody looked" must never be the same response. The **dependency hash excludes status**: a zone being deleted does not change what a rule points at, and a fingerprint that moved would claim the rule had been edited.

- **A batched lookup, because the obvious one is a load test on a neighbour.** `searchDiagnostics` resolves dependency status **once for the whole tenant** rather than per rule; a test creates ten rules and asserts one hierarchy call. The per-rule version passes every test written against three rules and falls over at four hundred. Now CONSTRAINTS §54.

- **History is a shift, not a time series.** A bounded 24×1h ring per rule, on the counter so it dies with the thing it describes, rolled at compile and read time and never per event. Prometheus already stores history properly; a second, worse, per-node, restart-losing one would have been permanent. Per-rule labels are deliberately not exported there — cardinality is the reason, and a bounded ring is the cheaper honest answer. A test asserts a year of idling costs a bounded walk rather than 31 million loop iterations, which the naive implementation would have done.

- **I did not do what rec 9 asked, and said so.** "Separate the Authoring, Operations and Runtime APIs" was implemented as a **module** split (`rule-authoring.ts` / `rule-operations.ts` / the bus consumer) with **no path renamed**. Prefixing published routes breaks every consumer, integration and runbook in exchange for tidier prose — §41, applied to the refactor that most often forgets it. A route test asserts every published path still resolves. The same reasoning kept `POST /rules/import` taking a bare `RulePackage` body with the new conflict policy as a query parameter. Now CONSTRAINTS §55.

What it delivers is everything P-5 needs to exist before it can be built against — and a matrix saying so, so the gate is checkable rather than remembered.

- **`assigned` is an operation, not a state.** G-1 listed Assign alongside Investigate and Escalate as lifecycle states. An incident can be assigned while raised, acknowledged, investigating or escalated, and re-assigned without moving — a status answers _where is this_, an assignee answers _whose is this_. Folding them together makes `assigned → resolved` and `resolved → assigned` both look legal and the transition table stops carrying information. Assign keeps its own route, permission and immutable stream; it simply does not change `status`. `investigating` and `escalated` **are** states and were added as such. Now CONSTRAINTS §56.

- **The enum extension broke three files, which is the good version of that failure.** Adding two values to `IncidentStatus` is not purely additive for a strict parser. In-repo it surfaced as a compile error in every console `Record<IncidentStatus, …>` — except `incident-card.tsx`, which had **re-typed the four values as a local string union** and would have silently rendered nothing. It now aliases the contract type, so the next change breaks the build there too. The enum is pinned by a test that must be edited deliberately.

Attachments are **references** (`evidence` id or `link` URI): copying an evidence record into an incident puts a mutable copy of an immutable artefact in another context. A **closed incident is sealed** — no transition, no assignment, no note, because "retained for audit" is only true if the record stops changing. Now CONSTRAINTS §57.

Behaviour search is served honestly by `eventType` and `category`; the missing id is **TD-23**, owned by the Rules context because it is a producer change. Now CONSTRAINTS §58.

- **The coverage model was wrong the obvious way, and the mistake is the interesting part.** Written as a yes/no question like the tenant and camera ones, the base cursor index `{tenantId, raisedAt, id}` made _any_ filter look served — it consumes the tenant and serves the sort — while walking every incident the tenant had ever raised. The model is now three-valued (`covered` / `bounded` / `scan`, and never `scan`), and an index only counts as narrowing if it consumes a key **beyond** the tenant prefix. A self-test asserts the model catches both a missing index and one truncated before the cursor. Now CONSTRAINTS §59.

- **TD-22 paid before the filters landed, verified three ways.** Nine new indexes, all ending in the `(raisedAt, id)` cursor pair. Declaration model always; **`explain()` against a real MongoDB — which was reachable, so it actually ran**: ten filters, each choosing its declared index, no `SORT` stage, no `COLLSCAN`; and a scale benchmark at 100/1k/10k/100k. The benchmark is labelled for what it is — the in-memory store, not a database — because presenting it as an index benchmark would be the fabricated-signal failure §52–55 exist to prevent.

- **Three P1-5 event indexes were already wrong, and fixing them is a migration.** `tenant_occurredAt`, `tenant_type_time` and `tenant_camera_time` stopped at `occurredAt` and abandoned the `(occurredAt, id)` sort every paged read performs. Re-declaring a name with different keys is an `IndexOptionsConflict` that fails the service **at boot**, so `ensureIndexes` drops and rebuilds a changed name — and an integration test recreates the P1-5 shape and proves the service still starts. Now CONSTRAINTS §60.

- **The event by-id index is non-unique on purpose, and there is no cache metric.** A unique `{tenantId, id}` would route a genuine id collision into `persist`'s duplicate-key branch, which reports "already stored" and skips publishing — silently dropping a real event to enforce a constraint nothing needed. Uniqueness stays with `dedupKey`. And rec 4 named four lookup series; three are emitted, because **there is no cache** and a `cache_hits_total` pinned at zero reads as a broken one.

- **G-5 closes the flagship gap.** `GET /events/:id` makes the investigation workspace's answer reachable end to end: incident → `triggeredBy.eventId` → the event → `POST /rules/:id/simulate` with `GET /rules/:id/incident-context`. `EventEnvelope` is untouched — frozen AI Runtime v1.0 contract; this is a query surface.

## ED-0060 — P-5.1 prerequisites: the coverage model that found the bug was itself wrong, and measuring is what caught it

- **Date:** 2026-08-03 · **Phase:** Product Capability layer (P-5.1) · **Architect direction:** P-5 architecture approved as the implementation blueprint; P-5.1 authorised to resolve findings F-1…F-6 plus the permission expansion, with seventeen recommendations — the first of which is _"never merge multiple milestones together; every milestone must remain independently reviewable."_

- **⚠️ The correction worth reading first.** TD-25 was raised by _reading_ the Evidence context's index list. Implementing it began by porting the three-valued coverage model from Workflow — which then declared the defective index **`covered`**, while `explain()` against a real MongoDB showed that same index producing a **blocking `SORT`**. Two corrections came out of it, and both are general: **the sort is a pair, not a key** (an index that reaches `capturedAt` and stops still hands the `_id` tiebreak to an in-memory sort), and **"unindexed" is not one failure — cardinality decides** (a residual predicate over a cursor walk costs `limit ÷ selectivity`: ~100 documents for a two-valued enum, the tenant's entire history for a near-unique id). The Workflow, camera and tenant models carry the weaker version; they are correct today by luck of their key sets. Now CONSTRAINTS §61.

- **TD-25 closed, measured.** Four new indexes for the identity filters, three rebuilt to carry the cursor pair, `ensureIndexes` reconciling a changed key set (an `IndexOptionsConflict` fails the service at boot — an integration test recreates the pre-P-5.1 shape and asserts the old index really did sort in memory). Verified four ways: coverage model, `explain()` planner assertions, an **examined/returned** assertion, and a MongoDB benchmark. Before: `eventId` examined **500 documents to return 1**. After: **1/1, flat from 10k to 500k rows**.

- **An actor's type is recorded, never inferred.** `IncidentActorRef {kind, id}` is written on every transition, assignment and note; `by` is untouched. ⚠️ Pre-P-5.1 records resolve to **`unknown`** — `"system"` is _probably_ the platform, and probably is the whole problem, because a person named system is an ordinary account. The one inference that is not a guess: a bare string arriving through a write path always meant the human making the request, so it normalises to `operator`. Now CONSTRAINTS §62.

- **The AI boundary is enforced twice, and neither is a convention.** The permission catalog is primary: no write permission an AI could hold, `incident:ai-recommend` granted to no role, and `REFUSED_INCIDENT_PERMISSIONS` naming `ai-resolve`/`ai-close`/`ai-assign` as permissions that **must never exist** — one that exists can be granted by an administrator who has not read the comment. The domain is secondary: `assertMayMutate` throws if an `ai-advisor` reaches a state-changing path, specifically so an AI action can never be written into an immutable audit trail where removing it means rewriting history. Four tests assert the catalog rather than the prose.

- **The activity enum models kinds, not a copy of another enum.** Sixteen activities were named; nine are the _payload_ of a kind — acknowledgement/investigation/escalation/resolution are `state-change` plus `transition.to`, which **is** `IncidentStatus`, and duplicating it leaves two enums to keep in sync forever. `Evidence Removed` was refused outright: evidence is immutable and attachments are append-only, so an enum value implying removal would advertise a capability that must not exist. AI accept/reject and camera/rule context changes are **deferred, not added** (§58 applied to an enum) and are safe to add later because every entry carries `kind`, `actor`, `at` and `summary` so consumers render an unknown kind rather than breaking.

- **The timeline has a budget, a timeout and typed gaps.** Three upstream calls maximum, never one per entry (§54); opt-in per source; a 2-second timeout each; and every absence reported as `unavailable`, `truncated` or **`not-requested`** — the last so a reader can always tell _there is nothing_ from _nobody asked_. The `TimelineSources` port **defaults to every source unavailable**, the P-4 pattern: a default returning empty arrays would claim the sources were consulted. Calls are sequential rather than parallel, because a timeline endpoint that fans out concurrently multiplies a retry storm across three neighbours at once. Now CONSTRAINTS §63.

- **No SLA policy means `unknown`, never `met`** — the failure avoided is a dashboard reporting 98% compliance for a deployment that never set a target. Derived from timestamps already stored, so changing a policy re-reports history rather than leaving stale verdicts. An incident resolved straight from `raised` counts that as attention; otherwise the metric punishes the fastest possible response.

- **`incident:close` was split additively, deliberately.** Separating it from `incident:resolve` lets a tenant enforce separation of duties — but _withholding_ it from `operator` would silently remove an ability every operator has today, which is a breaking behaviour change wearing a new permission's clothes. It is granted; a tenant that wants the separation revokes one grant. `incident:create`, `incident:reopen` and `incident:delete` were **refused**: incidents are only promoted from candidates, a closed incident is sealed (§57), and the history is immutable.

Each is its own milestone, and folding them into a slice about something else would break the discipline the same review opened by insisting on. ## ED-0061 — P-5.2.0: freeze the shapes, refuse the ones that cannot be honest, and check the permission before naming it

**Date:** 2026-08-03 · **Milestone:** P-5.2.0 (contract + specification freeze; **no implementation**) · **ADR:** [ADR-0031](../adr/ADR-0031-workspace-prerequisites.md)

Eleven recommendations arrived with the P-5.1 approval, all of the form _define the contract before
implementation_, plus three refinement sets during the work. All of it discharged as contracts and
specifications; **P-5.2 has not begun**.

**The finding is a permission this time, not a query.** The obvious name for reading the access
audit was `audit:read`. Both `operator` and `viewer` hold `*:read` — so that name would have granted
a log of _who viewed what, when, from which IP_ to the least privileged role in the product, **at
the moment the string was written**. No grant recorded. Nothing failing. No test asserting the
negative. Measured (`can(ROLE_PERMISSIONS.viewer, 'audit:read')` is `true`), renamed to
`audit:inspect`, and the hazard **pinned by an assertion that `audit:read` would have been granted**
— because avoiding an instance is not the same as recording the class. The class is worse than the
instance: **every** future `<resource>:read` is granted to viewers the moment it is named
([TD-26](../../tracking/TECH-DEBT.md)).

**What was refused, and the reasoning that generalises:**

- **Five of eleven requested audit events.** A write leaves a record; a read leaves nothing.
  Assignment, comment, attachment, resolution and escalation already append to the incident's own
  streams and are derived by `IncidentActivity` — a second copy is two records of one truth (§46).
  `view` refused separately: at list-row granularity it is one write per rendered row, and **a
  sampled audit is not an audit**, because the one access anybody asks about is the one dropped.
- **A global relevance score.** Search is a federation over per-context indexes; blending scores
  across them is arithmetic on incomparable quantities (§52). Groups state their own ordering.
- **Four "search entities".** Site/Building/Floor/Zone are the `type` of a `location` — four
  entities would copy the frozen hierarchy enum into search. `actor` is a _reference_, not a record.
- **A `partial` job state.** "Partly succeeded" is where the archive missing four clips gets handed
  to a regulator. A half-finished export is a failure that produced something.
- **A signed URL inside `JobResult`.** It outlives its own expiry: a broken link at best, a
  credential sitting in a queryable collection at worst.
- **A second design-system document.** One already existed and was already enforced; two
  descriptions of one visual language have no principled resolution when they disagree.

**Three restatements that changed the design:**

1. _"Persist only UI state"_ → **"a reference may be persisted; a record may not."** The
   instruction's own examples (current incident, selected evidence) crossed its line. An id goes
   stale safely; a cached `{id, status, title}` renders stale truth confidently after access is
   revoked.
2. _A keyboard registry and a command palette_ → **one registry.** A shortcut is a binding to a
   command; two tables diverge silently, and the failure is a keystroke firing a renamed command.
3. _A theme_ → **presentation that may not choose content.** If a theme could drop the audit trail,
   two reports of one incident would say different things while both claiming to be the report.
   Theme ids are opaque configured slugs, not an industry enum (§36).

**Also worth recording:** the design system's "Tailwind only, no Bootstrap, no MUI" rule was already
true — and true **by accident**. Nothing recorded it and nothing checked it, so the first
`pnpm add @mui/material` would have passed review as an ordinary dependency change. It is now a test
that reads the real manifest.

Constraints added: **§64** registers are data · **§65** four render states, the fourth being
_unavailable_ · **§66** references not records · **§67** federation budgets and no fabricated
ranking · **§68** audit reads, derive writes · **§69** naming a permission is a grant.

## ED-0062 — P-5.2: the joins run as the caller, and the freeze got the vocabulary wrong

**Date:** 2026-08-03 · **Milestone:** P-5.2 (Investigation Workspace) · **ADR:** [ADR-0032](../adr/ADR-0032-investigation-workspace.md)

**The finding came from writing the client, not from reviewing the contract.**

The timeline's three joins were the last unwired piece of P-5.1's F-3. The established pattern for a
service-to-service read is `HttpCameraSource`'s internal key, and using it here would have been a
one-line decision that nobody reviewed twice. It is also a **privilege escalation through a
read-only narrative**: the timeline would show an operator events, evidence and notifications they
cannot open in any other panel. Nothing errors; the Events panel refuses them and the timeline does
not, and the discrepancy reads as a bug in the panel.

So every join forwards the caller's own `Authorization`, and a request with no identity is
**refused, not upgraded** — asserted by a test that the upstream is never called, rather than that
the call fails.

**That made a frozen enum incomplete.** With caller-scoped joins, 403 is routine. `IncidentTimelineGapReason`
had `unavailable | truncated | not-requested`, and mapping a permission failure onto `unavailable`
tells an operator the events service is down — sending them to an engineer for something a role
grant fixes. `forbidden` was added, with the ⚠️ strict-parser caveat ADR-0029 records for
`IncidentStatus`; it is safe only because P-5.2 is the first consumer, and the next such extension
will not have that excuse.

Worth recording as a pattern: **P-5.2.0 froze nine contract modules and got the shapes right. The
one thing it got wrong was a vocabulary gap that only appeared when something had to answer with
it.** A freeze reduces the class of mistakes to exactly this kind, which is the argument for the
freeze — not against it.

**Two smaller decisions:**

- **The evidence join asks by `incidentId`, not by correlation.** Both are indexed, so this is not
  performance: the correlation spine can carry a **sibling incident's** evidence, and showing it as
  this incident's is wrong in the direction an investigator acts on.
- **`QueryBoundary` gained a fourth state** rather than gaining a sibling component. Two components
  deciding one thing would let a panel choose Empty where the contract says Unavailable — and the
  reason string comes from the registry, so it cannot.

Constraint added: **§70** — a cross-context join runs as the caller, and "you may not" is not "it is
down".

## ED-0063 — P-5.3: the client had never been measured, and the chain has to be able to break

**Date:** 2026-08-03 · **Milestone:** P-5.3 (evidence integration + collaboration) · **ADR:** [ADR-0033](../adr/ADR-0033-evidence-integration-and-chain.md)

**The finding was in the frontend build, and measuring first is the only reason it was found.**
Recommendation 17 said _continue measuring, never assume_. Measuring the production bundle **before
changing anything** showed the console shipped as **one chunk: 1,410 kB (403 kB gzip)** — the rule
editor, Recharts and the entire workspace downloaded before an operator could see the login form.
Nothing was broken. Nothing had ever been looked at. Route-level lazy boundaries plus vendor
chunking took the entry chunk to **42.9 kB (13.4 kB gzip)**.

⚠️ **The gate is a byte budget, which needed justifying against §51.** That constraint forbids
turning a recorded number into a threshold, because a benchmark belongs to the machine that produced
it. **Bytes are not milliseconds:** a bundle's size is reproducible from source and lockfile, so a
byte regression is a fact rather than a measurement artefact. A gzip budget was rejected for the
opposite reason — compression ratios move with the compressor version, reintroducing the machine
dependence. And the script **fails when `dist/` is missing** rather than skipping, because a budget
that passes for want of a build is §44 in a build script.

**The evidence chain's value is entirely in its breaks.** Three of the eight stages have no producer
in this build, and on most incidents a fourth is empty because automatic capture is a no-op pending
the media frame source (TD-15). A diagram that omitted the unbuilt stages would say the chain ends
at evidence; one that drew every gap identically would say the platform lost something. So an
unresolved stage carries a **required reason** from six — aged out · archived · never produced · not
built · forbidden · unreachable — and the schema refuses a link without one.

**Health is projected, not probed.** Seven probes on the busiest screen would re-answer what the
screen already knows from the timeline's typed gaps and the panel registry. The health panel fetches
nothing. It reports **three kinds of "not working"** — because a release, a config change and a page
to an engineer are three different actions — plus **`unknown`** for anything nothing exercised,
which is never drawn as healthy.

**Three requests were answered differently, each for a reason recorded in the ADR:** a third
`migrationVersion` was refused (no distinct question; the per-panel version is what actually meets
"never invalidate saved layouts"); "AI must not mutate without approval" was met by going further
(an AI cannot mutate _with_ approval, because an approval flow needs an AI-authored mutation to
exist); and "WebSocket-ready" was answered by reserving the vocabulary on the SSE transport that
already exists rather than standing up a second one for updates that are server→client only.

Constraints added: **§71** measure the client, gate what is deterministic · **§72** a composed status
is projected, never probed · **§73** a provenance chain must be able to break, and say which kind ·
**§74** a conflict is reported to the person, never retried.

## ED-0064 — P-5.4: a redaction that is only drawn is not a redaction

**Date:** 2026-08-03 · **Milestone:** P-5.4 (investigation reservations) · **ADR:** [ADR-0034](../adr/ADR-0034-investigation-reservations.md)

**The finding was in a feature list, in the word "annotation".** The reservation asked for
rectangles, polygons, arrows, text, **blur, redaction** and timestamps as one annotation layer.
Modelled that way, a redaction is a shape stored beside the media and painted over it at display
time — and the bytes still contain the face. Anyone with `evidence:read` sees it unobscured by
opening the original, using another viewer, or exporting through any path that does not consult the
investigation context. ⚠️ A disclosure copy is the **one** artefact where "the viewer chose not to
paint it" is the whole failure: handing a police force a file whose redaction is a rendering hint is
worse than handing them the original, because everyone involved believes it is redacted.

So the layer is split. Overlays are non-destructive and live with the investigation. `blur`, `mask`
and burnt-in `timestamp` are **treatments**: a `RedactionRequest` runs as a `media.render` job and
produces a **new evidence record** with its own hash and custody log. There is no
`overwriteOriginal` flag, and `RedactionResult.irreversible` is `z.literal(true)` — a treatment that
could be undone from the derived copy would mean the pixels were never removed. Now CONSTRAINTS §75.

**Three more requests were answered differently, each for a stated reason.**

⚠️ **The session field list is UI state.** `sessionId`, `resumeToken` and `expiresAt` read like a
server resource; the requirement's own last line ("restore only UI state, never business state")
resolves it. The token is an opaque encoding of a query and a position and is explicitly **not a
bearer credential** — restoring re-runs the query under the restorer's permissions, so a link pasted
into a chat cannot outlive the revocation of the person who made it. `activeBookmarks` and
`activeAnnotations` are **id lists, never records**: a persisted record survives the incident
closing, the annotation being revised and access being withdrawn, and is then rendered as current
(§76).

⚠️ **A 16-tile wall is a display grid, not a resolution budget.** Each sync member is a full session
resolution, so `PLAYBACK_SYNC_MAX_SOURCES` stays at 9 and a 16-grid resolves at most nine with the
rest drawn as empty tiles. `resolvableMembers()` derives from the constant so there is no second
number to maintain.

⚠️ **An export profile may require a redaction but never perform one.** A court profile differs from
an internal one by what has been _removed_, and removal is content; a profile that could redact
would be a presentation object silently changing evidence. `requiresRedactionReview` is a gate, and
`PROFILE_FORBIDDEN_KEYS` is asserted so no future change adds content selection (§77). The seven
profiles ship as **data, not an enum** — six jurisdiction nouns in the type system is what §36
refuses.

**And two metrics could not be computed at all.** A **false negative** is an incident that was never
raised: there is no document to count, so a dashboard computing `0` from platform data states the one
thing it cannot know, on the metric a customer is most likely to buy on. It is reported with a source
and a date, and absent means _not measured_ (§79). ⚠️ **Operator workload is staff monitoring** — the
same finding as `audit:read`, one milestone later in a friendlier costume: `metrics:workload` takes a
distinct action verb so no `*:read` wildcard reaches it, and the aggregate form naming nobody stays on
the ordinary read path (§78). `OperatorWorkload` carries no quality measure on purpose: an operator
does not choose which incidents reach them.

**The general lesson.** Four of these were found by asking what a field would be _true of_ rather
than what it would _contain_. A feature list is written in the vocabulary of the screen; a contract
has to be written in the vocabulary of the guarantee, and the two disagree most sharply exactly where
the guarantee matters most.

## ED-0065 — P-5.4.1: three timestamps, four view modes, and a derivation you can reproduce

**Date:** 2026-08-03 · **Milestone:** P-5.4.1 (final architecture review) · **ADR:** [ADR-0034 addendum](../adr/ADR-0034-investigation-reservations.md)

Seven refinements arrived as the last architecture review before implementation. **Three were already
satisfied** and were recorded as such rather than reimplemented — optimistic concurrency with honest
conflict resolution (§74, P-5.3), never mutating originals (§75), and lazy loading with a bundle
budget (§71). Reimplementing a satisfied requirement is how a codebase acquires two answers to one
question.

**Four were genuine gaps, and three of them are the same mistake in different clothes: a single value
standing in for several distinct facts.**

⚠️ **One timestamp gets read as the wrong one.** An exported clip carrying only an export date is a
file that says the wrong thing about when the events in it happened — "exported at 14:05" is received
as a claim about the world. Split into `recordedAt` · `playbackOffsetSeconds` · `exportedAt`, with
clock confidence defaulting to `unknown` and an estimated alignment carrying its caveat **out of the
platform**. A caveat that does not survive the export was never worth making (§81).

⚠️ **Two view modes cannot describe four artefacts.** `original | enhanced` had nowhere to put a
redacted copy, so a redacted copy would have shown as `original` — §75's failure one layer up, where
the operator concludes the bystander was never in frame. Now four, and `viewMode()` **checks
provenance before adjustment**: brightening a redacted clip does not make it "enhanced", it makes it a
brightened redaction, and the stronger claim is the one that belongs on screen (§82).

⚠️ **`sourceEvidenceId` alone does not make an artefact reproducible.** It says what the input was, not
whether today's renderer would produce the same output — a blur radius or a scaling filter that
changed between releases yields a visibly different file from identical inputs. `DerivedArtifact`
carries `rendererVersion` and the **ordered** operations, ordered because rendering is not
commutative: masking then downscaling is not the picture downscaling then masking produces, and the
second order can leave recoverable detail at a region's edge. It also **refuses an output id equal to
its input** — a derivation whose output is its input is an in-place mutation wearing a provenance
record, which is precisely the shape a well-meaning optimisation would take (§80).

**The fourth is about what survives.** A report needs `templateVersion` (the slug `security` in 2026
and in 2029 are the same name and possibly a different document) and the **integrity hash of every
evidence item included**. Evidence is immutable, so an id looks sufficient — but an item can be
**purged under retention**, and a report re-rendered afterwards is a different document that looks
identical. ⚠️ Both are required on `RenderedReport` via a refinement and left **optional on
`ReportProvenance`**, because `ReportPreview` shares that shape and is computed before anything is
rendered. Requiring them on the artefact that leaves the building is the additive way to get the
guarantee; requiring them on the shared shape would have been a breaking change for no gain (§83).

**The general lesson, and it is the same one as ED-0064.** Every gap here was found by asking what a
field would be **true of** rather than what it would contain. A feature list names things the screen
shows; a contract has to name the claim each value makes to whoever receives it — and the two diverge
hardest exactly where the artefact outlives the session that made it.

## ED-0066 — P-5.5: the review page found what the tests could not

**Date:** 2026-08-03 · **Milestone:** P-5.5 (evidence playback) · **ADR:** [ADR-0035](../adr/ADR-0035-evidence-playback.md)

The first implementation milestone after the architecture freeze, and it added **no contract** — the
only change inside `@vip/contracts` was flipping ten `WORKSPACE_COMMANDS[…].available` flags from
`false` to `true`, because a player now consumes them and that field exists to say what a deployment
can actually do.

⚠️ **The two defects that mattered were found by rendering the components and looking at them**, not
by the 167 console tests that were already passing.

**1. Every H.264 clip was declared undecodable.** The player probed
`canPlayType('video/mp4; codecs="h264"')`. That parameter is RFC 6381 — `avc1.42E01E` — and this
platform's manifests store the _friendly_ name, because `CameraCodec` is `'h264' | 'h265'`. Measured
in Chromium: the friendly form answers `''`, the RFC form answers `probably`, the bare container
answers `maybe`. So the player would have told every operator that every real clip in the product
could not be played, and the unit tests could not have caught it: jsdom answers `''` to everything,
so a rendered-outcome assertion would only ever have proved jsdom's stub. The test that pins it now
asserts **the string handed to the browser**, with Chromium's measured answers mocked in. Now §86.

**2. The timeline axis was an unreadable smear.** `MAX_TICKS` was 24. At a realistic panel width a
ten-minute range picks a 30-second step, which puts twenty `02:31 PM` labels across ~700 px at 35 px
each. Ten fits. Edge labels are now dropped rather than clipped — a centred label at 0 % renders as
a truncated time, and `02:4` is worse than no label.

**Three decisions that were not mechanical.**

⚠️ **Watching evidence is accessing evidence** (§84). `playbackSession` issues a signed URL exactly
as `download` does, so it appends a custody entry with `via: 'playback'`. Omitting it would have
produced a chain of custody that says nobody opened a clip an investigator reviewed a hundred times.

⚠️ **Capabilities are read off the media** (§85), and two are permanently false: no renderer extracts
a still and no packager builds an export. `frameStep` deliberately under-claims — it needs a declared
codec, because keyframe density is not knowable from a manifest.

⚠️ **Bookmarks got their own collection and their own sort order.** Notes live on the incident
document because they are bounded by design; bookmarks are not, are wanted only when a player is
open, and would make every queue listing carry playback detail. Their index ends in `(at, id)`
**ascending** — the opposite of every incident index — because a bookmark list is read oldest-first,
as a route through the footage. And an unconfigured store **refuses** rather than returning `[]`: an
empty list tells an operator they have bookmarked nothing (§44).

**One thing was deliberately not done.** Bookmarks and evidence metadata went _inside_ the panels
that already own them rather than taking two new panel ids. The registry is frozen at seventeen, and
the freeze permits a contract change only for a real implementation problem — this was not one.

**A test-harness gap, fixed once.** `renderWithProviders` omitted `TooltipProvider`, which `App.tsx`
supplies. Any component using a tooltip was therefore untestable, and the failure read as a component
bug rather than a harness gap. The test tree now matches the real tree.

**The general lesson.** ED-0064 and ED-0065 were found by asking what a field would be _true of_.
These two were found by **looking at the rendered pixels**. A test asserts what you thought to
assert; a screenshot shows what you shipped — and the browser-capability defect was invisible to the
test environment by construction.

## ED-0067 — P-5.6: measure it, then stop believing the measurement

P-5.6 was a production-verification milestone, not a feature one: browser validation, touch, memory,
recovery, real media. It added no contract. The only change inside `@vip/contracts` is one
`available` flag flipped to `true`, because a player now consumes `Mod+B`.

Five things were learned, and three of them contradicted a decision made one milestone earlier.

⚠️ **The P-5.5 fix was right and insufficient.** §86 said: probe the container, never append the
stored codec name. Correct — every engine answers `''` to `codecs="h264"`. But `video/mp4` answers
`maybe` in **all five engines**, so a container-only check can never refuse the format nearly all
CCTV arrives in. An H.265 clip on a build with no HEVC decoder fell straight through to _"the media
could not be loaded"_ — the same sentence a dead signed URL produces. The friendly name is now
_translated_ into representative RFC 6381 candidates rather than dropped. §86b.

⚠️ **`hvc1` and `hev1` are not interchangeable, and one engine proves it.** Safari answers `probably`
to `hvc1` and `''` to `hev1`; Chrome and Firefox accept both. Probing a single string would have
reported "Safari cannot play H.265", which is false. Each codec carries a list and the best answer
wins. The general shape: **a capability question may need several phrasings before the answer means
what you think.**

⚠️ **A positive probe is not a promise.** WebKit and Safari answered `probably` to `avc1.42E01E` and
then rejected an actual H.264 file with `MEDIA_ERR_SRC_NOT_SUPPORTED`. So the check may **refuse**
and may never **promise** — `unsupported` is actionable, `supported` is only advice, and `unknown`
is never a synonym for either (§44, §87). The failure classification gained a `refused` case whose
copy says exactly that, because "try a different browser" is advice an operator can act on and "the
media could not be loaded" is not.

⚠️ **The most consequential finding: a damaged recording plays silently.** Truncated and
byte-corrupted H.264 played in Chromium, Chrome and Firefox with **no error event of any kind**,
reporting roughly half the duration. An investigator watches the clip stop and concludes the incident
ended there. Nothing in the browser will ever tell them otherwise, so the platform does: where the
playhead stopped is compared against the duration the evidence record declares, and a shortfall is
stated persistently, pointing at the integrity hash. It compares the **playhead**, not the reported
duration — the same intact file reports 6.01 s, 3.45 s and 1.19 s across three engines. §88.

⚠️ **The leak was not where the intuition put it.** "Opening hundreds of clips leaks memory" turned
out to be unmeasurable: over 250 open/close cycles, retained nodes and JS heap were indistinguishable
between releasing the element and not (148 vs 193 nodes; 0.025 vs 0.026 MB). Decoded media does not
live on the JS heap. What _is_ measurable is the download — 60 clips opened and closed as soon as
their metadata arrived transferred **13.33 MB unreleased against 1.61 MB released**, because a
detached element with a live `src` keeps fetching. The first draft of this entry claimed a heap leak;
the A/B measurement removed the claim. **State what the measurement showed, not what motivated it.**

### Four defects the tests could not have found, and two more from driving the UI

1. **The player was a black rectangle forever.** The media release ran on ref cleanup — and React
   runs ref cleanup then re-attach on a node that is _still mounted_. It cleared `src` on a live
   element and React never restored it, because its virtual DOM saw no change. Now deferred a
   microtask and guarded on `isConnected`. The same investigation found that the _obvious_ home for
   the cleanup — an unmount effect — silently does nothing, because React nulls refs before passive
   cleanups run.
2. **4,000 bookmarks clustered to the right number and looked wrong.** 67 abutting pins are a solid
   band hiding the footage, the gaps and the playhead. Past a density the timeline draws a density
   band instead. §91: bounding the count is necessary and not sufficient.
3. **An iPad got 32 px controls** — `sm:` is screen width, and an iPad Pro is 834 px wide. Touch
   capability is a property of the pointer. §90.
4. **The volume slider was unreachable on touch**, because it was revealed on hover.
5. **Pinch-zoom silently did nothing** — `setPointerCapture` throws for a pointer the browser no
   longer tracks, and the uncaught throw aborted the handler before the gesture registered.
6. **The transport stayed live under every error overlay.** §85 applied to capabilities; it now
   applies to states too.

### One deliberate structural change

The keyboard handler no longer switches on `event.key`. P-5.5 read the frozen registry's chords in a
comment and re-typed them into a `switch` — two tables holding the same bindings, with the help sheet
documenting one and the code implementing the other. The registry is now _executed_: a chord is
normalised, looked up in the `playback` scope, dispatched by command id. The shortcut sheet renders
the same data. A binding cannot be implemented one way and documented another.

### And what was refused

The milestone asked for validation against Hikvision, Dahua, CP Plus, UNV, ONVIF, RTSP and NVR
playback. **None of it was done and none of it was simulated.** No such hardware exists here, and a
fixture named after a vendor would put that vendor's name against behaviour it never produced.
Separately, and more importantly: **no browser plays RTSP**, so live camera playback is not a testing
gap but a missing server-side component. `docs/review/p56/NVR_VALIDATION.md` says so plainly, because
"playback is production-ready" must be read as _recorded evidence playback is production-ready_.

**The general lesson.** ED-0066 said a screenshot shows what you shipped. P-5.6 adds the next step:
a measurement shows what the platform does, and then you have to ask what the measurement is
actually evidence of. `probably` was evidence of a parser's opinion, not of a decoder. A shorter
duration was evidence of metadata, not of damage. A retained node count was evidence of nothing at
all.
