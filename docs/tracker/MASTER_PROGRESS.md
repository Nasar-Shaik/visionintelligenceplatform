- **AI-5d Health Monitoring, Auto-Recovery & Model Lifecycle ✅ code+tests complete, ⏳ awaiting review** (plan approved + 8 further recommendations; **17 recommendations total** folded in). **In `ai/inference`, no new service; frozen five untouched; no new architectural layer** — AI-5d _supervises_ stages that already exist. AI-5b made a session survive its **camera**, AI-5c its **neighbours**; AI-5d makes it survive **itself over time**. **`HealthMonitor`** replaces the healthy/unhealthy bit with a **0–100 score decomposed across connection · inference · scheduler · resources · recovery** (every component **required** in the output — a report that omits a subsystem is the one that misdirects an operator), each indicator carrying a `Trend` so health reports where it is **heading**; a projected decline becomes one more pressure reason on the governor's existing path, because **health decides nothing** — two components able to degrade a session independently is how you get undebuggable oscillation. **`AutoRecovery`** **executes the frozen AI-5b taxonomy** within a **budget expressed as configuration**: retail 3 restarts · factory 10 · bank unlimited-with-long-cooldown · **healthcare never auto-restarts** — all four shipped as deployment profiles; `configuration` failures are **never retried**, enforced as a code-level invariant that _rejects_ a profile asking for it. **`RecoveryReason`** records trigger · subsystem · severity · retry count · correlation id, and **every refusal is recorded too**. **Progressive restoration** replaces ladder reversal: each degradation pushes a **`RestoreStep`** recording exactly what it removed and each recovery pops it, making exact-reverse restoration **structural rather than intended**. **Anti-oscillation** is **direction-aware** — a reversal waits out a stabilization window, but two escalations in a row are the ladder doing its job and are never delayed (this correction surfaced when a naive guard broke two existing scheduler tests). **`ModelLifecycleManager`** stages every version change `warming → validating → switching → draining → active` with rollback on the same mechanism run backwards; zero downtime rests on one indirection — the analyzer holds a **`ModelSlot`** read **per frame**, so promotion is an attribute assignment and no session stops. - **AI-5e Production Certification Framework ✅ code+tests complete, ⏳ awaiting review** — the **final milestone of AI Runtime Architecture v1.0** and, per the Architect, the **last AI runtime milestone (no AI-6)**. Explicitly redefined by the Architect: _"The software can build the framework. Real hardware validates the framework"_ — and re-prioritized so **accuracy on recorded CCTV footage outranks hardware certification**. **In `ai/inference`, no new service, no new layer; frozen five untouched.** The organising idea is **`EvidenceClass`** (`simulated` → `recorded-footage` → `hardware`) threaded through every check, report and promotion, with three rules made **structural rather than conventional**: a report is only as strong as its **weakest** check; **`certified` is unreachable without `hardware`**; **`production` maturity is unreachable without `hardware`**. A complete run against a simulated source — every check green — still returns `pending-validation`, and a **negative control** asserts it, because a framework that can certify itself from its own simulations converts a known unknown into a false assurance someone will quote to a customer. - **P-2 Camera Lifecycle, Identity & Operational Health ✅ code+tests complete, ⏳ awaiting review** — P-1 produced an inventory, which records what somebody _configured_ and says nothing about whether it works; every camera ever onboarded showed `health: unknown` because nothing had opened a stream. P-2 answers "does it work?" and, more importantly, fixes **what the platform is entitled to claim when it answers**. The rule (**[ADR-0024](../adr/ADR-0024-camera-lifecycle-evidence-gate.md)**, **[CONSTRAINTS §25](../project/CONSTRAINTS.md)**): the lifecycle states that describe a physical device — `connected` · `monitoring` · `degraded` · `offline` — may only be entered from a **measurement of that physical device** (`EvidenceClass: hardware`); `discovered` · `validated` · `configured` are declared; `retired` is administrative and **not reversible by a health check**, because a camera someone deliberately decommissioned must not quietly re-enter the estate when a scheduled probe happens to reach it. This is §18 — the AI-5e rule that a simulation never certifies hardware — applied to devices instead of capabilities, and it closes the door through which that failure would otherwise have re-entered. The measurement is `POST /streams/validate`, which returns an **ordered check report** (`reachability → authentication → stream-open → frames-received → codec → resolution → fps → latency → jitter`) where a failure leaves every later check **`not-executed`, never `fail`** — the difference between an installer reading "connection failed" and re-running cable, and reading "✓ reachable · ✗ credentials rejected · – stream not attempted" and fixing a password in a minute. Four supporting decisions: **`EvidenceClass` lifted to `contracts/common/evidence.ts`** so certification, maturity, benchmarks and the device lifecycle read one enum; **device identity separated from network identity** — the ONVIF endpoint UUID the WS-Discovery parser was already reading _and discarding_ is now captured and matched **first**, so a camera whose DHCP lease moved is recognised (`addressChanged`) instead of onboarded twice; **capabilities cached with their provenance**, because without recording what they were read against, "has anything changed?" is unanswerable; **one bounded timeline, not two**, because the things that explain a state change are usually not themselves state changes. **A gap the tests exposed:** identity matching was fully unit-tested and **inert end to end** — nothing persisted a device's identity, so the DHCP case could never fire; `CreateCameraInput.identity` closed the loop. - **P-2.2 Operational Evidence ✅ code+tests complete, ⏳ awaiting review** — a probe stops being **the latest reading** and becomes **a piece of evidence**. Every probe used to erase the one before it, which makes the most common operational question — _was it always like this?_ — permanently unanswerable: a camera taking four seconds to first frame is unremarkable if it always did and an incident if it took 300 ms last week, and only one of those readings survived. Reports now live in an append-only `camera_probes` collection, each self-describing (probe id · per-camera `sequence` · provider · probe version · runtime version · evidence class · correlation id · the configuration snapshot it ran against · the identity it ran against · a backward pointer to its predecessor). **There is no update path against that store** (**[CONSTRAINTS §27](../project/CONSTRAINTS.md)**): a correction is a new record, retention drops whole reports, and `evicted` makes a trimmed archive self-declaring. **Replay reconstructs, it never re-measures** (§28) — a pure function over a record with no camera, network or probe port in scope, behind a `GET`; support work happens days after a failure, often on a camera since power-cycled into working, and re-probing then answers "it works now" without explaining anything. The transport table became a **validation provider registry** (§29): RTSP · HTTP · WebRTC · SRT · recorded video · DVR export · NVR playback · USB camera · edge stream all run the one staged pipeline, and a new source type is a `register_provider(...)` row rather than a second validation path that would grow its own definition of "connected". **Drift is classified, not listed** — codec, resolution, FPS, profile and security changes stay `unexpected` **even under a firmware upgrade**, because nobody upgrades a camera intending to lose a stream profile and "explained by the upgrade" is how the one investigable event stops being investigated. **Operational confidence is a device reliability score, never an AI confidence**, computed from availability · failure frequency · probe success · capability stability · identity stability · recent recovery, with `insufficient-evidence` carrying **no score at all**. - **P-2.3 Chain of Custody ✅ code+tests complete, ⏳ awaiting review** — the foundation could already prove what it measured; it could not yet **explain itself**. The Architect drew a line between _"we created indexes"_ and _"the planner will use them"_ and asked for the second — and those turn out to be very different claims.
