# G-3.5 — Manual Verification Guide

> Operator-executable runbook to reproduce the G-3.5 validation. **Part A** is the fast, deterministic
> path (no infrastructure). **Part B** is the full live walk-through on the dev stack. Companion to the
> [validation report](G-3.5-VALIDATION.md). Dev credentials are **dev-only** (never production).

---

## Part A — Deterministic harness (2 minutes, no infra)

Proves the whole backend spine with no camera, Mongo, or NATS.

```bash
# from the repo root
pnpm --filter @vip/e2e test          # 7 files, 33 tests — the full G-3.5 suite
pnpm --filter @vip/e2e typecheck     # strict TS across the composed spine
```

**Expected:** `Test Files 7 passed · Tests 33 passed`. To see the performance baseline printed, run the
standalone script pattern in the report §12, or read the numbers in the test.

What each file proves is listed in [validation report §14](G-3.5-VALIDATION.md#14-automated-integration-tests-deliverable).

## Part B — Live dev-stack walk-through (camera → alert vertical)

### B0. Prerequisites

```bash
node -v            # ≥ 22
pnpm -v            # 11.17.0
cp .env.example .env   # if not already present (dev-only secrets)
```

### B1. Bring up infrastructure + seed data

```bash
pnpm dev:stack     # Mongo, Redis, MinIO, NATS (docker compose)
pnpm seed          # seeds tenant slug `dev`, org, one user per role, + sample camera/rule/event/incident/alert
                   # login (DEV ONLY): admin@vip.dev / 123456  (also owner@vip.dev, operator@vip.dev, viewer@vip.dev)
pnpm dev:all       # starts every service + the Operations Console (turbo, concurrency 15)
```

Wait until health is green (each service logs `listening` and `consumer started`). The console is at
the printed local URL.

### B2. Log in

Open the console URL, sign in with the seeded admin (tenant `dev` · `admin@vip.dev` / `123456`). Confirm
the dashboard loads (Events, Incidents, Alerts panels).

### B3. Verify the pipeline per scenario

For each scenario, **inject the event**, then confirm it appears at every downstream stage. Two ways to
inject:

- **Perception (person/fire/smoke)** — publish a `DetectionResult` to the capability-output subject
  (`t.{tenantId}.capability.output.{capabilityId}`) via the NATS CLI or a small script; the events
  service normalises + persists it.
- **Producer (camera-offline/fight/queue/ppe/loitering/theft)** — publish a semantic `EventEnvelope`
  to `t.{tenantId}.event.{type}` (models the boundary noted in TD-1/TD-2).

> Fixture payloads for all nine scenarios are in [`tools/e2e/src/scenarios.ts`](../../tools/e2e/src/scenarios.ts)
> — copy the `makeEntry(...)` output as the message body.

**Verification checklist (repeat per scenario):**

| Stage           | How to check                                | Expected                                                              |
| --------------- | ------------------------------------------- | --------------------------------------------------------------------- |
| Event persisted | `GET /events?type=<type>` (or Events panel) | one envelope, correct `type` + `category`, `correlationId` set        |
| Rule matched    | rules service log / `rule.matched` subject  | the scenario's rule fired                                             |
| Incident raised | `GET /incidents` (or Incidents panel)       | one incident, expected severity, `triggeredBy.eventId` = the event id |
| Alert delivered | `GET /notifications` (or Alerts panel)      | one notification, `status: delivered`, `incidentId` = the incident id |
| Traceability    | inspect the incident + notification         | `correlationId` identical to the event's                              |
| Dashboard       | refresh the console                         | event, incident, and alert all visible                                |

### B4. Verify tenant isolation

Seed or provision a **second** tenant. Inject an event for tenant A. Confirm tenant B's dashboard shows
**nothing** new, and that calling `GET /incidents` with tenant B's token never returns A's incident
(cross-tenant path access → **403**).

### B5. Verify duplicate handling

Inject the **same** perception detection twice (same camera + capturedAt + label). Confirm **one** event,
**one** incident, **one** alert (dedup collapsed).

### B6. Verify failure behaviour

Publish a malformed payload to `t.{tenant}.event.perception.person.detected`. Confirm the rules service
logs a dead-letter (`term`) and **no** incident is created; then inject a valid detection and confirm
the pipeline still produces an alert (recovery).

### B7. Tear down

```bash
# Ctrl-C the dev:all process, then:
pnpm dev:stack:down
```

---

## Acceptance

Manual verification passes when **every** scenario in B3 shows event → incident → alert with a
consistent `correlationId` and correct traceability, isolation holds (B4), duplicates collapse (B5), and
poison messages are dead-lettered without wedging the pipeline (B6) — matching the automated results in
Part A.
