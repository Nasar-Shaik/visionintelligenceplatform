# P-4.1 — Rule Operations, Diagnostics & Portability

**Status:** code + tests complete · ⏳ awaiting architectural review
**Authorized:** 2026-08-03 (Architect, P-4 approval + 15 recommendations)
**Layer:** Product Capability — operational surface over the frozen foundations, redesigning none of them.

---

## What this is for

P-4 made rules usable. This makes them **supportable**: the questions asked at 2 a.m. and on the day a
customer retires a building — _is the rule on that node the one we signed off? what breaks if I delete
this zone? is this rule doing anything? put it back the way it was._

None of it touches how a rule decides. Nothing added here is read during evaluation, and nothing here
may become so.

### Rules service

- **`domain/fingerprint.ts`** — canonical serialisation + `contentHash` · `scopeHash` ·
  `dependencyHash` · `validationHash`. Pure, deterministic, inert.
- **`domain/dependencies.ts`** — `ruleDependencies`, including references made _inside_ conditions.
- **`domain/budget.ts`** — `measureRule` · `budgetChecks` · `rawDepth` (the pre-parse crash guard).
- **`domain/audit.ts`** — `deriveAudit`, including `rolled-back` detected from content.
- **`application/rule-stats.ts`** — `RuleStatsRegistry`, handing out counter references so the hot path
  increments a field it already holds.
- **`RuleSetCache`** — `refresh` (warm-up) · `statsFor` · hit/miss/coalesce/eviction counters.
- **`RuleStore.restore`** + `restoreVersion` — rollback that can remove a field.
- **`RuleDiagnostics`** port — live numbers supplied by the composition root, never a reference to the
  engine.
- **Routes** — `GET /rules/:id/audit` · `/dependencies` · `/compilation` · `GET /rules/dependents` ·
  `GET /rules/stats` · `GET /rules/export` · `POST /rules/import` · `POST /rules/:id/simulate` ·
  `POST /rules/:id/rollback`.

### Console

Version history is now an **audit timeline with restore**. The explanation view renders the server's
stage tree instead of re-deriving which stage decided.

## ⚠️ Three defects found in approved code

Each is fixed, and each has a test that fails without the fix.

1. **Editing an enabled rule bypassed the activation gate.** P-4 gated the _transition_ into `enabled`,
   so re-scoping a **live** rule to a deleted zone was accepted — and because re-scoping drops the
   expansion by design, the rule went unresolved and **matched nothing**. A live rule silently stopped
   firing.
2. **Mongo `$set` never removed a deleted field.** The domain deletes `resolvedScope` on a re-scope so
   the engine stops matching removed zones; `$set` left the stored value in place, so the rule kept
   firing on the **old** zones. Fixed with a paired `$unset`.
3. **A deeply nested body crashed the handler** inside the recursive Zod parser, before any check could
   report it. Fixed with an iterative pre-parse depth guard — verified by disabling the guard and
   watching the test fail.

The first two share a shape: correct domain behaviour defeated by the layer underneath it.

## The nine decisions

Recorded in full in [ADR-0027](../adr/ADR-0027-rule-operations-diagnostics-and-portability.md).

1. **Diagnostics are derived, never stored** — including the audit trail, which reads the versions the
   platform has always written rather than adding a second record of the same truth.
2. **A content hash excludes lifecycle** — a paused rule is the same rule.
3. **Live behaviour is gated, not the transition into it.**
4. **Rollback restores content, not state, and appends.**
5. **Statistics cost nothing per event, outlive compilation, and are honest about being per-node.**
6. **Budgets are enforced at validation, never during evaluation.**
7. **The simulation contract is frozen; the achievable half is implemented and the rest returns 501.**
8. **Imported rules always land as drafts.**
9. **The explanation tree is a projection of one evaluation, never a second one.**

## Benchmark

[RULE_ENGINE_BASELINE](../architecture/RULE_ENGINE_BASELINE.md) — 100 / 500 / 1,000 / 5,000 rules.
Per-rule cost is flat (81.7 ns → 85.6 ns); 5,000 rules compile in ~2.5 ms; 20,000 events, one store call.

⚠️ Those numbers are a **baseline for comparison on that machine**, not thresholds. The regression gate
asserts the _ratio_, which a slow CI runner does not move.

## P-5 readiness (rec 15)

Everything Incident Management needs from the Rule Designer, and where it comes from. **No P-5 work
requires a change here.**

| P-5 needs            | Available as                                  | Route                                                  |
| -------------------- | --------------------------------------------- | ------------------------------------------------------ |
| Rule id + version    | `IncidentCandidate.ruleId` / `.ruleVersion`   | already on the candidate                               |
| Scope snapshot       | `Rule.resolvedScope` on the immutable version | `GET /rules/:id/versions`                              |
| Evaluation trace     | `RuleExplanation` incl. `tree`                | `POST /rules/:id/dry-run`, `/simulate`                 |
| Dependency graph     | `RuleDependencyGraph` · `RuleDependents`      | `GET /rules/:id/dependencies`, `GET /rules/dependents` |
| Rule metrics         | `RuleStatsReport`                             | `GET /rules/stats`                                     |
| Audit trail          | `RuleAuditEntry[]`                            | `GET /rules/:id/audit`                                 |
| Compilation metadata | `RuleCompilation`                             | `GET /rules/:id/compilation`                           |
| Runtime statistics   | `RuleRuntimeStats` · `RuleCacheStats`         | `GET /rules/stats`                                     |

**The one thing P-5 will want and cannot have yet:** an explanation for an incident that _already
happened_. Explanations are derived on demand from an event, and the incident candidate carries the
triggering event's id, not the event. Reconstructing one means fetching the event from the Events
context — a P-5 decision about how the investigation workspace reaches other contexts, not a gap in the
Rule Designer. Recorded here so it is a decision rather than a surprise.
